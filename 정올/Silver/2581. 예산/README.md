## 1. 문제

`N`개 지방의 예산요청과 국가예산 총액 `M`이 주어진다. **총액 `M`을 넘지 않으면서 배정 합계를 최대로** 만들어야 한다.

- 모든 요청을 다 줄 수 있으면 요청한 금액 그대로 배정한다.
- 다 줄 수 없으면 **정수 상한액**을 하나 정해서, 그 이상을 요청한 지방에는 상한액을, 그 이하를 요청한 지방에는 요청액을 배정한다.

출력은 **배정된 예산들 중 최댓값**이다.

### 입력

```
첫 줄     N        (지방의 수)
둘째 줄   N개의 정수 (각 지방의 예산요청)
셋째 줄   M        (국가예산 총액)
```

### 출력

배정된 예산들 중 최댓값.

### 제한

- `3 ≤ N ≤ 10,000`
- `1 ≤ 각 요청액 ≤ 100,000`
- `N ≤ M ≤ 1,000,000,000`
- 시간 1초 / 메모리 32MB

### 예제

```
[입력]
4
120 110 140 150
485

[출력]
127
```

`상한액 = 127`이면 배정은 `120, 110, 127, 127`이고 합이 484다. 128로 올리면 `120 + 110 + 128 + 128 = 486 > 485`라 안 된다.

```
[입력]
5
70 80 30 40 100
450

[출력]
100
```

요청 합계가 `320 ≤ 450`이라 **전부 그대로 배정**된다. 이때 답은 상한액이 아니라 **가장 큰 요청액 100**이다.

## 2. 접근

### 관찰

- **상한액 `L`을 하나 정하면 배정 총액이 바로 계산된다.** `total(L) = Σ min(요청액ᵢ, L)`. "최댓값을 구하라"가 **"이 `L`이 가능한가?"라는 예/아니오 판정**으로 바뀐다.
- **`total(L)`은 `L`이 커질수록 단조 증가한다.** 그래서 `total(L) ≤ M`을 만족하는 `L`은 `0`부터 정답까지 **연속 구간**을 이룬다.

  ```
  L:      0   1   2  ...  ans  ans+1  ...  최대요청액
  가능?   O   O   O  ...   O     X     ...      X
  ```

  이 `OOO...OXXX...X` 모양이 곧 **이분탐색을 써도 된다는 근거**다. 경계 하나만 찾으면 된다.
- **규칙 (1)과 (2)를 분기할 필요가 없다.** 이 문제에서 제일 헷갈리는 지점인데, **탐색 범위의 오른쪽 끝을 `최대요청액`으로 잡으면 두 규칙이 저절로 하나의 식에 합쳐진다.**

  | 상황 | 마지막으로 성공한 `L` | 배정 결과 | 배정된 예산의 최댓값 |
  | --- | --- | --- | --- |
  | 요청 합계 `≤ M` | `L = 최대요청액` | 전부 요청액 그대로 | `최대요청액` = `L` |
  | 요청 합계 `> M` | `L = 상한액` | `L`보다 큰 요청은 `L`로 깎임 | `L` |

  두 경우 모두 **답 = 마지막으로 성공한 `L`**이다. 아래쪽 줄에서 "최댓값 = `L`"이 성립하는 건 합계가 `M`을 넘는다는 게 곧 **`L`보다 큰 요청이 존재한다**는 뜻이라서다. 그래서 "합계가 `M` 이하면 최댓값을 출력, 아니면 이분탐색" 같은 **예외 처리가 아예 필요 없다.**
- **`L`을 선형 탐색하면 안 된다.** `L`의 범위가 `0 ~ 100,000`이고 후보마다 판정에 `O(N)`이 드니 `10^5 × 10^4 = 10^9`이다. 이분탐색이면 `log2(100,000) ≈ 17`회, `17 × 10^4 = 1.7 × 10^5`으로 끝난다. (실측 반복 횟수도 정확히 17회였다)
- **여기서는 합계가 `int`에 들어간다.** 최악이 `10^4 × 10^5 = 10^9`이고 `int` 상한은 약 `2.1 × 10^9`이다. [나무꾼 미르코](../5170.%20나무꾼%20미르코/README.md)에서는 같은 자리에서 `long`이 필요했는데(합이 최대 `10^15`), 이 문제는 `N`과 요청액 상한이 둘 다 작아서 **우연이 아니라 계산상 안전하다.** 다만 여유가 2배뿐이다.
- **답이 0인 경우는 존재하지 않는다.** `M ≥ N`이고 각 요청액이 `1` 이상이므로 `L = 1`이면 `total(1) = N ≤ M`이 **항상** 성립한다. 즉 `L = 1`은 언제나 가능하고 답은 최소 1이다. `ans`의 초깃값 0은 실제로 출력될 일이 없다.

### 아이디어

정답인 상한액 자체를 탐색 공간으로 두고 이분탐색한다. 배열의 **원소**를 찾는 게 아니라 **답의 후보 범위**(`0 ~ 최대요청액`)를 쪼개는 파라메트릭 서치다.

중간값 `half`에서 `total(half)`를 계산해서

- `total(half) <= M` → **가능하다.** `ans = half`로 기록하고, 더 큰 상한액도 되는지 보려고 `minBudget = half + 1`로 올린다.
- `total(half) > M` → **초과다.** 상한액을 낮춰야 하므로 `maxBudget = half - 1`.

`total(half) == M`을 따로 잡지 않는 것이 중요하다. 예제 1에서 정답 상한액 127의 배정 합계는 **484로 485에 못 미친다.** `M`을 정확히 맞추는 상한액은 대개 존재하지 않으므로, `<= M`으로 묶고 "가능하면 일단 기록하고 더 욕심낸다"로 처리한다.

### 알고리즘 선택

| 후보 | 가능 여부 | 채택 |
| --- | --- | --- |
| `L`을 0부터 최대요청액까지 선형 탐색 | `10^5 × 10^4 = 10^9` → 1초 안에 불가능 | X |
| 답의 범위를 이분탐색 (파라메트릭 서치) | 17회 × `O(N)` = `1.7 × 10^5` | **O** |
| 규칙 (1)/(2)를 분기해서 따로 처리 | 동작은 함 | X: 탐색 상한을 최대요청액으로 두면 저절로 합쳐진다 |
| 정렬 + 접미사합 + 경계 이분탐색 | 판정이 `O(log N)`으로 떨어짐 | X: 정렬 비용이 더 크다 (7번 실측) |

**자료구조**: 요청액은 `int[]` 하나로 충분하다(`10^4 × 4B = 40KB`). 정렬은 [나무꾼 미르코](../5170.%20나무꾼%20미르코/README.md)에서 쓴 조기 종료 습관이 남아 넣었는데, **이 코드는 정렬해두고도 매번 전체를 훑기 때문에 아무 값도 하지 않는다.** 7번에서 실측으로 따진다.

## 3. 설계

### 동작 순서

```
1. N 입력 / cities[N] 입력하면서 maxBudget = 최댓값 기록
2. M 입력
3. minBudget = 0, maxBudget = 최대요청액, ans = 0
4. while (minBudget <= maxBudget):
   4-1. half = (minBudget + maxBudget) / 2
   4-2. totalBudget = Σ min(cities[i], half)
   4-3. totalBudget > M 이면 → maxBudget = half - 1            // 상한을 낮춘다
        아니면              → ans = half, minBudget = half + 1  // 더 올려본다
5. ans 출력
```

`ans`에 **성공한 `half`를** 기록하는 게 포인트다. 루프가 끝난 시점의 `minBudget`/`maxBudget`을 해석하는 대신 "가능하다고 확인된 값"만 남기므로, 경계 계산을 헷갈려도 답이 틀어지지 않는다.

두 가지를 같이 봐야 한다. **(가) `else`에서 `minBudget`을 반드시 올린다** — 안 올리면 구간이 줄지 않아 무한 루프다. **(나) 기록하는 값은 `half`(상한액)이지 `totalBudget`(배정 합계)이 아니다.** 첫 제출에서 이 두 개를 한꺼번에 놓쳤다 → 6번.

### 엣지 케이스

전부 로컬에서 직접 돌려 확인했다.

- **요청을 전부 배정할 수 있는 경우** — `4 / 120 110 140 150 / 520`(합계와 같은 총액) → `150`. `M = 10^9`으로 키워도 `150`. 관찰 3번대로 별도 분기 없이 맞는다. 검증 완료.
- **`M`이 최소인 경우 (`M = N`)** — `3 / 100000 100000 100000 / 3` → `1`. `L = 1`에서 `total = 3 = M`이고 `L = 2`는 `6 > 3`이라 실패. 검증 완료.
- **요청액 편차가 큰 경우** — `3 / 1 1 100000 / 3` → `1`. 작은 요청 둘은 그대로, 큰 요청만 1로 깎인다. 검증 완료.
- **`N`이 최소인 경우** — `3 / 1 1 1 / 3` → `1`. 이분탐색은 원소 개수와 무관하게 답의 범위만 쪼개므로 그대로 동작. 검증 완료.
- **`M`을 정확히 맞추는 상한액이 없는 경우** — 예제 1이 바로 그 경우다(484 vs 485). `<=` 비교라 문제없다. 검증 완료.
- **합계의 `int` 오버플로** — 최악 `10^4 × 10^5 = 10^9 < 2,147,483,647`이라 발생하지 않는다. 계산으로 확인.
- **`(minBudget + maxBudget) / 2`의 오버플로** — `minBudget ≤ 100,001`, `maxBudget ≤ 100,000`이라 합이 최대 `200,001`이다. 발생하지 않는다.
- **요청액이 여러 줄에 걸쳐 들어오는 경우** — `readLine()` 한 번으로 전부 읽는 지금 코드는 **런타임 에러**가 난다. 실제로 재현했다.

  ```
  $ printf '4\n120 110\n140 150\n485\n' | java Main
  Exception in thread "main" java.util.NoSuchElementException
      at java.base/java.util.StringTokenizer.nextToken(StringTokenizer.java:347)
      at Main.main(Main.java:19)
  ```

## 4. 복잡도

| 구분 | 복잡도 | 근거 |
| --- | --- | --- |
| 시간 | O(N log N + N log C) | 정렬 `10^4 × 14 ≈ 1.4 × 10^5`, 이분탐색 `log2(10^5) ≈ 17`회 × `N = 10^4` 스캔 = `1.7 × 10^5`. 제한 1초에 비해 압도적으로 여유 |
| 공간 | O(N) | `int[10,000]` = 40KB. `int[]` 정렬은 제자리(dual-pivot quicksort)라 추가 배열이 없음. 제한 32MB |

`log`가 두 종류라는 걸 구분해야 한다. `log N`은 **정렬**에서 나오고, `log C`(`C` = 요청액 상한 `100,000`)는 **답의 범위**를 쪼개는 데서 나온다. 이 문제는 두 값이 `10^4`, `10^5`으로 비슷한 규모라 정렬과 탐색 비용이 같은 자릿수에 놓인다 — 정렬이 공짜가 아니라는 뜻이고, 7번의 근거가 된다.

### 실측 (N = 10,000 무작위, M = 10^9, 로컬 JDK 17)

제출 환경과 같은 **JIT 워밍업 없는 단발 실행**에서 단계별로 재봤다.

| 단계 | 시간 | 비고 |
| --- | --- | --- |
| 입력 파싱 | 11.5 ~ 12.4 ms | `BufferedReader` + `StringTokenizer` |
| `Arrays.sort` | 3.1 ~ 3.7 ms | **이분탐색 전체보다 오래 걸린다** |
| 이분탐색 (17회 × 10,000 스캔) | 2.0 ~ 2.1 ms | 원소 접근 총 170,000회 |
| 전체 실행 (JVM 기동 포함) | 202 ~ 207 ms | |

읽는 방법이 두 가지다.

- **알고리즘은 전혀 문제가 아니다.** 실제 계산은 2ms고 나머지 200ms는 JVM 기동이다. 제한 1초 안에서 이 문제는 사실상 무엇을 해도 통과한다.
- **그래도 정렬 3.2ms는 순수한 낭비다.** 정렬을 지우고 다시 재보니 이분탐색은 `2.0 ~ 2.1 ms`로 **완전히 동일**했다. 정렬이 탐색을 1%도 빠르게 하지 못한다는 직접적인 증거다.

## 5. 코드

```java
import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;
import java.util.Arrays;
import java.util.StringTokenizer;

public class Main {

    public static void main(String[] args) throws IOException {
        BufferedReader br = new BufferedReader(new InputStreamReader(System.in));

        // 국가 예산 총액 배정
        // 정해진 총액 이하에서 가능한 한 최대의 총 예산을 각 지방에 분배하는 문제
        // 규칙 1) 모든 요청이 배정될 수 있는 경우에는 요청한 금액 그대로를 배정
        // 규칙 2) 모든 요청이 배정될 수 없는 경우 -> 특정한 정수 상한액을 계산 -> 그 이상인 예산 요청에는 모두 상한액을 배정 AND 상한액 이하는 요청한 금액을 그대로 배정

        // 지방의 수(N): 3 ~ 10,000, 각 지방의 요청예산: 최대 100,000, 총 예산(M): 최대 10억개
        int N = Integer.parseInt(br.readLine());
        StringTokenizer st = new StringTokenizer(br.readLine());
        int minBudget = 0;
        int maxBudget = Integer.MIN_VALUE;
        int[] cities = new int[N];

        for (int i = 0; i < N; i++) {
            int city = Integer.parseInt(st.nextToken());

            maxBudget = Math.max(maxBudget, city);
            cities[i] = city;
        }


        int M = Integer.parseInt(br.readLine());


        /**
         * 계획 1
         * - 이분탐색으로 중앙값을 계산 -> 중앙값을 예산 상한선으로 설정
         * - 예산 상한선을 반영해서 각 지방에 분배될 총 예산을 계산
         * - 총 예산이 M보다 크면 중앙값을 더 작게 계산 (maxBudget = half-1)
         * - 총 예산이 M보다 작거나 같으면 중앙값을 더 크게 계산 (maxBudget = half+1)
         */

        Arrays.sort(cities);

        int ans = 0;
        while (minBudget <= maxBudget) {
            int half = (minBudget + maxBudget) / 2;
            int totalBudget = 0;

            // 중앙값보다 작거나 같으면 신청 예산, 중앙값보다 크면 중앙값으로 배정
            for (int i = 0; i < N; i++) {
                totalBudget += cities[i] <= half ? cities[i] : half;
            }

            // 분배할 총 예산이 M보다 크면 상한선을 더 낮춤
            if (totalBudget > M) {
                maxBudget = half - 1;
            }
            // 분배할 총 예산이 M보다 작거나 같으면 상한선을 높혀봄
            else {
                minBudget = half + 1;
                ans = Math.max(ans, half);
            }
        }


        System.out.println(ans);
    }

}
```

## 6. 삽질 기록

| 시도 | 결과 | 원인 | 고친 것 |
| --- | --- | --- | --- |
| 1 | 시간 초과 (무한 루프) | 성공 분기에서 `minBudget`을 갱신하지 않아 구간이 줄지 않음 + `ans`에 상한액이 아니라 배정 총액을 기록 | `else`에 `minBudget = half + 1`을 넣고 `ans = Math.max(ans, half)`로 바꿈 |
| 2 | 통과 | | |

### 시도 1 — 틀린 코드

성공 분기가 이렇게 한 줄이었다.

```java
if (totalBudget > M) {
    maxBudget = half - 1;
}
else {
    ans = Math.max(ans, totalBudget);   // minBudget 갱신 없음 + 기록하는 값도 다름
}
```

**한 줄에 서로 다른 버그가 두 개 겹쳐 있다.** 하나씩 떼어놓고 봐야 구분이 된다.

### 버그 A — `minBudget` 갱신 누락 → 무한 루프

이분탐색의 진행은 오직 **구간이 줄어드는 것**에 달려 있다. `totalBudget > M`일 때는 `maxBudget`이 줄지만, `else`에서는 `minBudget`도 `maxBudget`도 건드리지 않는다. 그러면 다음 반복의 `half`가 **직전과 완전히 같은 값**이 되고, 같은 값이면 같은 분기로 들어가므로 상태가 영원히 고정된다.

예제 1을 추적해보면 **첫 반복에서 이미 갇힌다.**

```
iter=1  [0, 150] half=75 total=300 <= M   -> else, 아무것도 안 바뀜
iter=2  [0, 150] half=75 total=300 <= M   -> 동일
iter=3  [0, 150] half=75 total=300 <= M   -> 동일
...        (30회에서 강제 중단)
```

`while (minBudget <= maxBudget)`은 `0 <= 150`으로 계속 참이다. **루프 조건이 잘못된 게 아니라 조건을 거짓으로 만들 주체가 없는 것**이라, 채점 결과는 오답이 아니라 시간 초과로 나온다.

> 이 문제에서는 무한 루프가 **항상** 발생한다. `L = 1`은 언제나 가능하므로(2번 관찰의 마지막 항목) 구간이 아무리 좁아져도 `else` 분기를 반드시 한 번은 만나고, 만나는 순간 갇힌다. 운 좋게 통과할 입력이 없다.

### 버그 B — 최대화 대상과 출력값을 혼동

버그 A를 고쳐 `minBudget = half + 1`을 넣어도 **여전히 오답이다.** `ans`에 `half`(상한액)가 아니라 `totalBudget`(배정 합계)이 들어가 있기 때문이다.

| 입력 | 시도 1의 출력 | 정답 | 시도 1이 출력한 값의 정체 |
| --- | --- | --- | --- |
| 예제 1 | `484` | `127` | 상한액 127로 배정했을 때의 **합계** |
| 예제 2 | `320` | `100` | 요청 5개를 전부 배정한 **합계** |

484라는 숫자가 특히 함정이다. **문제 본문에 "그 합이 484로 가능한 최대가 된다"고 적혀 있어서**, 출력해놓고도 틀렸다는 걸 알아채기 어렵다.

원인은 문제를 읽는 방식에 있었다. 문제는 "총액 이하에서 **가능한 한 최대의 총 예산을 배정**한다"고 말하므로 최대화의 대상은 분명히 **총액**이다. 하지만 출력하라는 것은 **"배정된 예산들 중 최댓값"**, 즉 상한액이다.

- **최대화 대상 (목적함수)**: `total(L)` → 판정에만 쓴다
- **출력값**: `L` → `ans`에 기록해야 하는 값

`totalBudget`은 "이 `L`이 가능한가"를 판정하기 위한 **중간 계산값**일 뿐이다. 그걸 답으로 착각한 것이다. 파라메트릭 서치에서 `ans`에 넣을 값은 **언제나 탐색 중인 파라미터(`half`) 자신**이고, 판정 함수의 결과가 아니다.

### 고친 뒤

```java
else {
    minBudget = half + 1;              // 버그 A: 구간을 줄인다
    ans = Math.max(ans, half);         // 버그 B: 파라미터 자신을 기록한다
}
```

두 줄을 넣자 예제 1은 `127`, 예제 2는 `100`으로 바로 통과했다. 결과적으로 [나무꾼 미르코](../5170.%20나무꾼%20미르코/README.md)에서 세 번 틀리며 정리한 표준형(`ans = half` 기록 + `half ± 1` + `minBudget <= maxBudget`)으로 돌아온 셈이다. **틀 자체는 기억하고 있었는데 `ans`에 무엇을 담는지를 놓쳤다.**

### 완전탐색과 교차 검증

이분탐색은 "예제는 맞는데 반례가 있는" 상태가 흔하므로, `L`을 `0`부터 최대요청액까지 전부 시도하는 완전탐색을 따로 짜서 비교했다.

```
무작위 20만 건 (N = 3~10, 요청액 1~40, M = N ~ 합계+10)
→ 불일치 0건
```

`M`이 합계보다 큰 경우(전부 배정)와 작은 경우(상한 발생)가 모두 섞인 입력이다. 예제 두 개만 맞춰보고 넘어가는 것과는 확신의 종류가 다르다.

## 7. 개선할 점

**1. `Arrays.sort`가 아무 일도 하지 않는다**

정렬을 넣은 이유는 나무꾼 미르코에서 쓴 "뒤에서부터 훑다가 `half` 이하를 만나면 멈춘다"는 조기 종료였다. 그런데 **이 코드의 루프는 `i = 0`부터 `N-1`까지 무조건 전부 돈다.** 정렬된 순서를 쓰는 곳이 한 군데도 없다.

| | 정렬 | 이분탐색 | 합계 |
| --- | --- | --- | --- |
| 정렬 O (현재 코드) | 3.2 ms | 2.0 ms | 5.2 ms |
| 정렬 X | 0 ms | 2.0 ms | **2.0 ms** |

`min`을 취한 합계는 **순서와 무관**하다(`Σ min(aᵢ, L)`은 더하는 순서를 바꿔도 같다). 그래서 정렬은 지워도 답이 100% 동일하다. 한 줄 지우면 끝이다.

```java
long total = 0;
for (int x : cities) total += Math.min(x, half);
```

`Math.min`을 쓰면 `cities[i] <= half ? cities[i] : half`라는 삼항 연산자보다 의도("둘 중 작은 쪽을 배정한다")가 바로 드러난다.

**2. 정렬을 쓸 거라면 접미사합까지 가야 본전이다**

정렬의 진짜 값어치는 **"`half`보다 큰 요청들"이 뒤쪽 연속 구간이라는 사실**에 있다. 그러면 경계 인덱스를 이분탐색으로 찾아 누적합으로 판정을 `O(log N)`에 끝낼 수 있다.

```java
long[] pre = new long[N + 1];                    // pre[i] = cities[0..i-1]의 합
for (int i = 0; i < N; i++) pre[i + 1] = pre[i] + cities[i];

int k = upperBound(cities, half);                // cities[k] > half 인 첫 인덱스
long total = pre[k] + (long) (N - k) * half;     // 앞쪽은 요청액 그대로 + 뒤쪽은 half
```

원소 접근이 `170,000회 → 225회`로 줄어드는 것까지 실측으로 확인했다. 그런데도 **채택하지 않는 게 맞다.**

- 전체 시간은 여전히 정렬(3.2ms)이 지배한다. 판정에서 2ms를 아껴도 정렬로 3.2ms를 내면 남는 게 없다 → **1번(정렬 제거)이 더 낫다.**
- 메모리 32MB에 `long[10,001]` = 80KB는 아무 문제가 없다. 나무꾼 미르코(16MB에 `long[10^6]` = 8MB)와 달리 **여기서 이 방법을 접는 이유는 메모리가 아니라 순수하게 수지가 안 맞기 때문이다.**

이 방법은 `L`을 여러 번 질의해야 하는 변형 문제에서 값을 한다.

**3. `ans = Math.max(ans, half)`는 `ans = half`로 충분하다**

`Math.max`는 "혹시 나중에 더 작은 값이 덮어쓰지 않을까?" 하는 걱정에서 나온 방어인데, 그 상황은 **구조적으로 생길 수 없다.** 성공해서 `ans = half`를 기록하는 순간 `minBudget = half + 1`이 되므로, 이후의 모든 `half`는 `half + 1` 이상이다. 즉 **성공한 `half`는 항상 직전 성공값보다 크다.**

```java
ans = half;   // 성공값은 단조 증가하므로 Math.max가 필요 없다
```

`Math.max`가 남아 있으면 읽는 사람이 "어떤 경우에 작아질 수 있지?"를 한참 고민하게 된다. **불필요한 방어 코드는 없는 불변식을 있는 것처럼 보이게 만든다.**

여기에 `Math.max`가 남은 건 6번의 시도 1에서 `ans = Math.max(ans, totalBudget)`이었던 흔적이다. `totalBudget`을 기록할 때는 `Math.max`가 필요해 **보였지만**(그때도 실은 단조 증가였다), `half`로 바꾼 뒤에는 껍데기만 남았다.

**4. `totalBudget`은 `long`으로 받는 습관을 들이기**

지금은 최악이 `10^9`으로 `int`에 들어가므로 **틀린 코드가 아니다.** 다만 여유가 2배뿐이라, `N`이나 요청액 상한이 조금만 커지면 조용히 음수가 되어 오답이 난다. 나무꾼 미르코에서 정확히 이 자리에서 무한 루프까지 갔다. `long`으로 두면 판정식 `totalBudget > M`에서 `M`이 자동 승격되므로 나머지 코드는 손댈 필요가 없다.

**5. 입력이 여러 줄로 나뉘어도 죽지 않게**

3번에서 재현했듯 요청액이 두 줄에 걸치면 `NoSuchElementException`으로 죽는다. 지금 통과하는 건 입력이 한 줄이었기 때문이지 코드가 옳아서가 아니다. `StreamTokenizer`는 줄바꿈을 신경 쓸 필요가 없고, 실측상 파싱 시간(12ms)도 줄어든다.

```java
StreamTokenizer in = new StreamTokenizer(new BufferedInputStream(System.in));
in.nextToken(); int N = (int) in.nval;
```

전체 200ms 중 파싱이 12ms니 속도 이득 자체는 작다. **죽지 않는다는 게 더 중요하다.**

**6. `maxBudget = Integer.MIN_VALUE` 초깃값**

요청액이 `1` 이상이라고 문제에 못 박혀 있으므로 `0`으로 두면 된다. `Integer.MIN_VALUE`는 "음수도 들어올 수 있다"는 신호를 잘못 준다. `minBudget = 0`과 짝을 맞춰 `maxBudget = 0`으로 시작하는 편이 읽기 좋다.

**7. `minBudget + (maxBudget - minBudget) / 2` 형태로 쓰기**

이 문제는 합이 최대 `200,001`이라 `(minBudget + maxBudget) / 2`가 안전하다. 하지만 상한이 `10^9`대인 문제에서는 그대로 터진다. **값이 같으면서 덧셈 오버플로가 없는 형태를 이분탐색 기본형으로 손에 붙여둘 것.**

## 8. 배운 것

**`ans`에 기록할 값은 탐색 중인 파라미터 자신이다.** 판정 함수의 결과(`totalBudget`)는 예/아니오를 만들기 위한 중간 계산값일 뿐인데, 문제가 "총 예산을 최대로"라고 말하니 그쪽을 답으로 착각했다(6번 버그 B). **최대화하는 대상과 출력해야 하는 값이 다른 문제**가 있다는 걸 기억할 것. 문제를 읽고 나서 "무엇을 최대화하는가"와 "무엇을 출력하는가"를 따로 한 줄씩 적어두면 걸러진다.

**이분탐색에서는 모든 분기가 구간을 줄여야 한다.** 성공 분기에서 `minBudget`을 올리지 않으면 `half`가 그대로 남아 같은 분기를 무한히 반복한다(6번 버그 A). 나무꾼 미르코에서는 `maxBudget = half`(`-1` 누락)로, 이 문제에서는 갱신 자체를 빼먹어서 — **두 문제 연속으로 같은 자리에서 무한 루프를 냈다.** 이분탐색을 쓸 때 `if`/`else` 양쪽을 보면서 "이 분기는 구간을 줄이는가?"를 소리내어 확인할 것.

**파라메트릭 서치에서 실제로 정하는 것은 "판정 함수"와 "탐색 범위의 양 끝"이다.** 이 문제에서 규칙 (1)/(2) 분기가 사라진 이유가 그것이다. 오른쪽 끝을 `최대요청액`으로 잡는 순간 "전부 배정 가능"이 **탐색 범위의 오른쪽 끝이 성공하는 경우**로 흡수돼서 예외 처리가 필요 없어진다. 범위를 잘 잡으면 특수 케이스가 특수하지 않게 된다.

### 나무꾼 미르코와 비교 — 방향이 반대인데 코드는 같다

| | 나무꾼 미르코 (5170) | 예산 (2581) |
| --- | --- | --- |
| 판정 함수 | `total(H) = Σ max(0, hᵢ - H)` | `total(L) = Σ min(reqᵢ, L)` |
| 단조성 | `H`가 커지면 **감소** | `L`이 커지면 **증가** |
| 가능 조건 | `total ≥ M` (적어도 M) | `total ≤ M` (M을 넘지 않게) |
| 가능한 값의 집합 | `[0, ans]` | `[0, ans]` |
| 루프 | 가능하면 올린다 | 가능하면 올린다 |

단조 방향과 부등호 방향이 **둘 다** 뒤집혀서, 결국 "가능한 값이 앞쪽 연속 구간"이라는 모양은 같아진다. 그래서 코드 골격을 그대로 재사용할 수 있었다. **파라메트릭 서치 문제를 만나면 단조성만 보지 말고 `단조 방향 × 부등호 방향`을 함께 따져서 `OOOXXX`인지 `XXXOOO`인지 먼저 그려볼 것.**

**정렬은 이유가 있을 때만 넣는다.** 앞 문제에서 쓴 도구를 습관적으로 가져오면 이렇게 값을 못 하는 코드가 남는다. 정렬을 넣기 전에 "정렬된 순서를 실제로 쓰는 줄이 어디인가?"를 자문하면 바로 걸러진다.
