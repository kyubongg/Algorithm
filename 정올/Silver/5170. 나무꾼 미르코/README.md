## 1. 문제

나무 `M`미터가 필요하다. 절단기의 높이 `H`를 설정하면 **`H`보다 높은 나무는 `H` 위쪽이 잘려 나가고**, `H` 이하인 나무는 그대로 남는다.
잘린 부분의 길이 합이 `M` 이상이 되도록 하면서, **`H`를 최대한 크게** 잡고 싶다. 그 `H`를 구한다.

> 핵심은 "정확히 `M`미터"가 아니라 **"적어도 `M`미터"** 라는 점이다. `M`을 딱 맞추는 `H`는 존재하지 않을 수도 있다.

### 입력

```
첫 줄     N M      (나무의 수, 필요한 나무 길이)
둘째 줄   N개의 정수 (각 나무의 높이)
```

### 출력

적어도 `M`미터를 얻을 수 있는 절단기 높이 `H`의 최댓값.

### 제한

- `1 ≤ N ≤ 1,000,000`
- `1 ≤ M ≤ 2,000,000,000`
- `1 ≤ 나무 높이 ≤ 1,000,000,000`
- 시간 1초 / 메모리 **16MB**

### 예제

```
[입력]
4 7
20 15 10 17

[출력]
15
```

```
[입력]
5 20
4 42 40 26 46

[출력]
36
```

## 2. 접근

### 관찰

- **`H`를 하나 정하면 얻는 길이는 바로 계산된다.** `total(H) = Σ max(0, 나무높이 - H)`. 즉 "최댓값을 구하라"는 문제를 **"이 `H`가 가능한가?"라는 예/아니오 검사**로 바꿀 수 있다.
- **`total(H)`는 `H`가 커질수록 단조 감소한다.** 그래서 `total(H) ≥ M`을 만족하는 `H`는 `0`부터 정답까지 **연속 구간**을 이룬다.

  ```
  H:      0   1   2  ...  ans  ans+1  ...  maxH
  가능?   O   O   O  ...   O     X     ...   X
  ```

  이 `OOO...OXXX...X` 모양이 곧 **이분탐색을 써도 된다는 근거**다. 경계 하나만 찾으면 된다.
- **선형 탐색은 불가능하다.** 답의 범위가 `0 ~ 10^9`인데 후보마다 `total(H)` 계산에 `O(N)`이 든다. 반면 이분탐색이면 `log2(10^9) ≈ 30`회, `30 × 10^6 = 3 × 10^7`으로 끝난다.
- **합은 반드시 `long`.** 최악은 높이 `10^9`짜리 나무 `10^6`개 → `10^15`. `int`(약 `2.1 × 10^9`)로는 어림도 없다. (실제로 여기서 한 번 틀렸다 → 6번)
- `M`은 상한이 `2,000,000,000`이라 `int` 최댓값 `2,147,483,647`에 **겨우** 들어간다. 여유가 7%뿐이다.

### 아이디어

정답 `H` 자체를 탐색 공간으로 두고 이분탐색한다. 보통은 배열의 **원소**를 이분탐색하지만, 여기서는 **답의 후보 범위**(`0 ~ 가장 높은 나무`)를 쪼갠다. 이걸 파라메트릭 서치라고 부른다.

중간값 `half`에서 `total(half)`를 계산해서

- `total(half) >= M` → **가능하다.** 일단 `ans = half`로 저장해두고, 더 큰 `H`도 되는지 보려고 `minH = half + 1`로 올린다.
- `total(half) < M` → **부족하다.** 절단기를 낮춰야 하므로 `maxH = half - 1`.

`total(half) == M`을 따로 잡을 필요는 없다. 예제를 조금 바꿔 `M = 6`으로 두면 `H = 15`에서 7미터, `H = 16`에서 5미터라 **6미터를 정확히 만드는 `H`가 아예 없다.** 등호를 종료 조건으로 쓰면 이런 입력에서 답을 못 찾는다. 그래서 `>= M`으로 묶고 "가능하면 일단 기록하고 더 욕심낸다"로 처리한다.

### 알고리즘 선택

| 후보 | 가능 여부 | 채택 |
| --- | --- | --- |
| `H`를 `maxH`부터 0까지 선형 탐색 | `10^9 × N` → 불가능 | X |
| 답의 범위를 이분탐색 (파라메트릭 서치) | 30회 × `O(N)` = `3 × 10^7` | **O** |
| 정렬 + 누적합 + 경계 이분탐색 | 30회 × `O(log N)`으로 더 빠름 | X: 정렬 비용이 더 크다 (4번 실측) |

**자료구조**: 높이는 `int[]` 하나면 충분하다(`10^6 × 4B = 4MB`). 정렬은 "`half`보다 큰 나무만 뒤에서부터 훑다가 멈춘다"는 **조기 종료**를 노리고 넣었는데, 이 판단이 옳았는지는 7번에서 실측으로 다시 따진다.

## 3. 설계

### 동작 순서

```
1. N, M 입력 / trees[N] 입력하면서 maxH = 최댓값 기록
2. trees 오름차순 정렬
3. minH = 0, maxH = 가장 높은 나무, ans = 0
4. while (minH <= maxH):
   4-1. half = (minH + maxH) / 2
   4-2. treeAmount = 0, idx = N-1
        trees[idx] > half 인 동안 뒤에서부터:
            treeAmount += trees[idx] - half
            idx--
        (정렬되어 있으므로 half 이하를 만나는 순간 그 앞은 볼 필요가 없다)
   4-3. treeAmount >= M 이면 → ans = half, minH = half + 1   // 더 높이 잘라본다
        아니면                → maxH = half - 1              // 낮춰서 더 얻는다
5. ans 출력
```

`ans`에 **성공한 `half`만** 기록하는 게 포인트다. 루프가 끝난 시점의 `minH`/`maxH`를 해석하는 대신 "가능하다고 확인된 값"만 남기므로, 경계 계산을 헷갈려도 답이 틀어지지 않는다.

### 엣지 케이스

- **`N == 1`** — `1 5 / 10` → `5`. 이분탐색이 원소 개수와 무관하게 답의 범위만 쪼개므로 그대로 동작. 검증 완료.
- **답이 0인 경우** — `M`이 전체 나무 길이 합과 같으면 땅바닥(`H = 0`)까지 다 베어야 한다. `2 2000000000 / 1000000000 1000000000` → `0`. `ans`의 초깃값이 0이라 별도 처리 없이 맞는다. 검증 완료.
- **`total`이 `int`를 넘는 경우** — `treeAmount`를 `long`으로 선언해서 해결. `2 4 / 1000000000 1000000000` → `999999998`. 검증 완료.
- **`M`을 정확히 만드는 `H`가 없는 경우** — `4 6 / 20 15 10 17` → `15`(7미터). 위에서 설명한 대로 `>=` 비교라 문제없다. 검증 완료.
- **`(maxH + minH) / 2`의 오버플로** — 여기서는 `minH ≤ 10^9 + 1`, `maxH ≤ 10^9`라 합이 최대 `2,000,000,001`로 `int` 안에 들어간다. **운 좋게 안전한 것**이지 안전한 코드는 아니다. 높이 상한이 `2 × 10^9`인 문제였다면 그대로 터진다.
- **높이가 여러 줄에 걸쳐 들어오는 경우** — `readLine()` 한 번으로 전부 읽는 지금 코드는 **런타임 에러**가 난다. 실제로 재현했다.

  ```
  $ printf '4 7\n20 15\n10 17\n' | java Main
  Exception in thread "main" java.util.NoSuchElementException
      at java.util.StringTokenizer.nextToken(StringTokenizer.java:347)
      at Main.main(Main.java:28)
  ```

## 4. 복잡도

| 구분 | 복잡도 | 근거 |
| --- | --- | --- |
| 시간 | O(N log N + N log H) | 정렬 `10^6 × 20 = 2 × 10^7`, 이분탐색 `log2(10^9) ≈ 30`회 × 최대 `N = 10^6` 스캔 = `3 × 10^7`. 실제 제출 358ms / 제한 1초 |
| 공간 | O(N) | `int[1,000,000]` = 4MB. `int[]` 정렬은 제자리(dual-pivot quicksort)라 추가 배열이 없음. 표기 제한 16MB / 실제 제출 45.4MB |

`log`가 두 종류라는 걸 구분해야 한다. `log N`은 **정렬**에서 나오고, `log H`는 **답의 범위**를 쪼개는 데서 나온다. 이 문제는 `H`의 범위(`10^9`)가 `N`(`10^6`)보다 크므로 반복 횟수가 30회로 잡힌다.

### 실측 (N = 1,000,000, 로컬 JDK 17)

| 입력 | 입력 파싱 | 정렬 | 이분탐색 | 실제 스캔한 원소 수 |
| --- | --- | --- | --- | --- |
| 모든 높이 = `10^9`, `M = 1` (최악) | 125 ms | 4 ms | **30 ms** | 29,000,000 |
| 무작위 높이, `M = 2 × 10^9` | 126 ms | **147 ms** | 5 ms | 1,041,728 |

전체 실행 시간은 JVM 기동을 포함해 약 450ms. 두 줄을 나란히 놓고 보면 이 코드의 성격이 드러난다.

- **최악 입력**(모든 나무가 똑같이 높고 `M`이 작을 때)에서는 조기 종료가 전혀 안 걸려 30회 × `10^6` = 2,900만 번을 그대로 훑는다. 그래도 30ms.
- **무작위 입력**에서는 정답이 최댓값 근처라 `half`보다 큰 나무가 몇 개 없어서 스캔이 104만 번으로 줄고 이분탐색이 5ms에 끝난다. 대신 **정렬에 147ms**가 든다.

즉 병목은 이분탐색이 아니라 **정렬과 입력 파싱**이다. 이 사실이 7번의 개선 방향을 결정한다.

## 5. 코드

```java
import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;
import java.util.Arrays;
import java.util.StringTokenizer;

public class Main {

    public static void main(String[] args) throws IOException {
        BufferedReader br = new BufferedReader(new InputStreamReader(System.in));

        // 나무 자르기
        // 나무가 M 미터 필요함, 톱날이 땅에서부터 H미터 위로 이동, 해당 높이까지의 나무들을 모두 자름

        // 나무의 최대 높이가 10억이기 때문에 나무의 최대 길이 ~ 0까지 반복하면 최대 10억번 반복해야함
        // 이분탐색 알고리즘으로 줄일 예정 -> 시간복잡도 : O(logN) : 최대 30번

        StringTokenizer st = new StringTokenizer(br.readLine());
        int N = Integer.parseInt(st.nextToken());
        int M = Integer.parseInt(st.nextToken());

        int[] trees = new int[N];
        int minH = 0;
        int maxH = 0;

        st = new StringTokenizer(br.readLine());
        for (int i = 0; i < N; i++) {
            int tree = Integer.parseInt(st.nextToken());
            trees[i] = tree;
            maxH = Math.max(tree, maxH);
        }

        Arrays.sort(trees);
//        System.out.println(Arrays.toString(trees));
        /**
         * 방법 1
         * - 땅: minH, 최대 나무 길이: maxH
         * - (minH + maxH) / 2로 잘랐을 때 의 값 : treeAmount
         * - treeAmount == M -> return treeAmount
         * - treeAmount < M -> maxH = half로 설정 후 한번 더 자름
         * - treeAmount > M -> 이것보다 더 작은 값이 있는지 찾기 위해서 더 윗부분을 잘라봄 -> minH = half
         */

        int ans = 0;
        int half = (maxH + minH) / 2;
        while (minH <= maxH) {
//            System.out.println(half);
            int idx = N-1;
            long treeAmount = 0;

            // 나무의 길이가 절반 값보다 클때 까지만 나무를 자를 수 있음
            while (idx >= 0 && trees[idx] > half) {
                treeAmount += trees[idx] - half;
                idx--;
            }

            // M과 자른 나무의 수가 크거나 같으면 위에 더 잘라보기
            if (treeAmount >= M) {
//                System.out.println("EQUAL: " + treeAmount);
                minH = half + 1;
                ans = half;

            }
            // 자른 나무의 수 < M -> 나무를 더 잘라보기
            else if (treeAmount < M) {
//                System.out.println("SMALL: " + treeAmount);
                maxH = half - 1;
            }

            half = (maxH + minH) / 2;
        }

        System.out.println(ans);
    }

}
```

## 6. 삽질 기록

| 시도 | 결과 | 원인 | 고친 것 |
| --- | --- | --- | --- |
| 1 | 오답 / 무한 루프 | `int treeAmount` 오버플로. 합이 최대 `10^15`인데 `int`에 담아 **음수**가 되고, 음수는 `< M`이라 탐색이 계속 아래로 내려감 | `treeAmount`를 `long`으로 |
| 2 | 오답 (0 출력) | `beforeCut`의 초깃값을 `Integer.MAX_VALUE`로 둠. 첫 `treeAmount`가 `2.1 × 10^9`을 넘으면 "이전보다 안 줄었다"고 판정해 **첫 반복에서 `break`**, `ans = 0` 출력 | `beforeCut` 휴리스틱을 **버리고** 표준 이분탐색으로 재작성 |
| 3 | 통과 (358ms) | | `>= M`이면 `ans = half` 기록 후 `minH = half + 1`, 아니면 `maxH = half - 1`. 종료 조건 `minH <= maxH` |

### 반례 하나로 세 버전 비교

```
[입력]
3 2000000000
1000000000 1000000000 1000000000

[정답] 333333333
```

| 버전 | 출력 | 반복 |
| --- | --- | --- |
| 시도 1 (`int treeAmount`) | **무한 루프** | 200회에서 강제 중단 |
| 시도 2 (`long`, `beforeCut = Integer.MAX_VALUE`) | **0** | 2회 |
| 최종 | `333333333` | 30회 |

`5 1 / 10^9 × 5`(정답 `999999999`)도 같은 결과다 — 시도 1은 `141006540`, 시도 2는 `0`.

### 시도 1은 왜 무한 루프였나

세 가지가 겹쳐야 무한 루프가 된다. 하나만 있었으면 오답으로 끝났을 것이다.

1. **`int` 오버플로로 `treeAmount`가 음수** → 항상 `treeAmount < M` 분기로 빠져 `maxH`만 계속 줄어든다.
2. **`maxH = half` (`half - 1`이 아님)** → 구간이 `[0, 0]`까지 줄어들면 `half = (0 + 0) / 2 = 0`, `maxH = 0`으로 **상태가 더 이상 변하지 않는다.**
3. **루프 조건이 항상 참** — `half > 0 || half <= maxH`에서 `half`는 `(minH + maxH) / 2`이므로 `minH <= maxH`인 동안 **`half <= maxH`가 무조건 성립**한다. 즉 조건식이 참/거짓을 판정하는 게 아니라 `true`를 쓴 것과 같고, 탈출은 오직 `break`에만 달려 있었다.

위 반례를 손으로 따라가면 이렇게 된다.

```
half=500000000 → 합 1.5e9 (int 안에 들어감) < M=2e9  → maxH=500000000
half=250000000 → 합 2.25e9 → int 오버플로 → -2044967296 < M → maxH=250000000
half=125000000 → 합 2.625e9 → 오버플로 → 음수 < M     → maxH=125000000
...
half=0         → 합 3e9 → 오버플로 → 음수 < M          → maxH=0, half=0
                 이후 minH=0, maxH=0, half=0 으로 영원히 고정
```

`시도 2`에서 `treeAmount`를 `long`으로 바꾸니 오버플로는 사라졌지만, 이번엔 `beforeCut`의 초깃값이 **같은 규모의 문제**를 일으켰다. `treeAmount`는 `long`인데 비교 기준만 `int` 상한에 머물러 있었던 것이다.

### 시도 2의 `beforeCut` 휴리스틱은 아이디어 자체가 틀렸나

**아니다. 초깃값만 문제였다.** `beforeCut = Long.MAX_VALUE`로 바꾼 버전을 무작위 4만 5천 건(`N ≤ 200`, 높이 `≤ 10^9`, 합이 `int`를 넘는 경우 포함)으로 돌려봤는데 반례가 나오지 않았다.

그런데도 최종 코드에서 이 방식을 **버린 게 맞다.**

- 종료가 `break`에만 달려 있다. 루프 조건이 항상 참이므로, 분기 하나만 잘못 건드리면 오답이 아니라 **무한 루프**로 터진다. 실패 모드가 너무 나쁘다.
- 상태가 `minH`, `maxH`, `ans`, `beforeCut` 네 개다. 표준형은 `minH`, `maxH`, `ans` 세 개고 그중 `ans`는 안전장치일 뿐이다.
- "이전보다 줄었는지"는 **답의 성질이 아니라 탐색 과정의 부산물**이다. 문제의 단조성(`total(H)`가 감소)을 직접 쓰는 대신 그 흔적을 추적하는 셈이라, 왜 맞는지 설명하기가 어렵다. 반례가 안 나온다는 것과 옳다는 것은 다른 말이다.

`treeAmount == M`에서 `break`한 것도 같은 성격의 착각이었다. 2번에서 봤듯 **`M`을 정확히 맞추는 `H`는 없을 수 있으므로**, 애초에 등호를 찾아 헤맬 필요가 없다. `>= M`으로 묶는 순간 `beforeCut`도, 조기 `break`도 전부 필요 없어진다.

## 7. 개선할 점

**1. 정렬이 오히려 손해다**

정렬을 넣은 이유는 "`half` 이하를 만나면 멈춘다"는 조기 종료였다. 그런데 4번 실측을 보면 계산이 맞지 않는다(무작위 입력, `N = 10^6`).

| | 정렬 | 이분탐색 | 합계 |
| --- | --- | --- | --- |
| 정렬 O (현재 코드) | 147 ms | 5 ms | **152 ms** |
| 정렬 X (매번 전체 스캔) | 0 ms | 40 ms | **40 ms** |

정렬로 아낀 탐색 시간은 35ms인데 정렬 값이 147ms다. **약 110ms 손해**다. 정렬은 `O(N log N)`을 **한 번** 내지만 조기 종료가 줄여주는 건 `O(N)` 스캔 30번 중 일부일 뿐이라, 애초에 수지가 맞지 않는다.

정렬 없이 이렇게만 써도 된다.

```java
long sum = 0;
for (int x : trees) if (x > half) sum += x - half;
```

**2. 정렬을 쓸 거라면 누적합까지 가야 본전이다**

정렬해놓고 여전히 `O(N)`으로 훑는 게 아까운 지점이다. 정렬의 진짜 값어치는 **"`half`보다 큰 나무들"이 뒤쪽 연속 구간이라는 사실**에 있고, 그러면 경계 인덱스를 이분탐색으로 찾아 **접미사 합**으로 한 번에 계산할 수 있다.

```java
long[] suf = new long[N + 1];                 // suf[i] = trees[i..N-1]의 합
for (int i = N - 1; i >= 0; i--) suf[i] = suf[i + 1] + trees[i];

int i = upperBound(trees, half);              // trees[k] > half 인 첫 인덱스
long sum = suf[i] - (long) (N - i) * half;    // 구간합 - (개수 × half)
```

이러면 이분탐색 한 회가 `O(N)`에서 `O(log N)`으로 떨어져 전체가 `O(N log N + log N log H)`가 된다.

다만 이 문제에서는 **두 가지 이유로 채택하지 않는 게 맞다.**

- 이 크기에서는 어차피 정렬 비용에 묻힌다 → **1번(정렬 제거)이 더 낫다.**
- **메모리 제한이 16MB다.** `long[10^6 + 1]`은 그것만 8MB고 `int[10^6]` 4MB를 더하면 12MB다. 자바는 실측 45.4MB로 통과했으니 실제로는 여유가 있었지만, 16MB라는 숫자는 "배열 하나로 풀어라"는 출제 의도다. `log H = 30`회를 아끼려고 메모리를 3배 쓰는 교환은 이 문제에선 손해다.

이 방법은 `H`를 여러 번 질의해야 하는 변형 문제에서 값을 한다.

**3. 입력은 `StreamTokenizer`로**

`readLine()` + `StringTokenizer` 조합은 두 가지 문제가 있다.

- 3번에서 재현했듯 **높이가 여러 줄에 걸치면 `NoSuchElementException`으로 죽는다.** 지금 통과한 건 입력이 한 줄이었기 때문이지 코드가 옳아서가 아니다.
- `10^6`개면 10MB짜리 `String` 하나와 토큰 문자열들이 통째로 힙에 올라간다.

```java
StreamTokenizer in = new StreamTokenizer(new BufferedInputStream(System.in));
in.nextToken(); int N = (int) in.nval;
in.nextToken(); long M = (long) in.nval;
```

줄바꿈을 신경 쓸 필요가 없어지고, 실측으로도 입력 파싱이 125ms → 108ms로 줄었다. 속도 이득 자체는 크지 않지만 **죽지 않는다는 게 더 중요하다.**

**4. `M`은 `long`으로 받기**

`M ≤ 2,000,000,000`이 `int` 상한 `2,147,483,647`에 겨우 들어간다. 지금은 맞지만 **상한이 조금만 커지면 조용히 음수가 되어 오답이 난다.** `treeAmount >= M` 비교에서 `M`이 `long`으로 승격되므로 타입만 바꾸면 나머지는 그대로 둬도 된다.

**5. `half` 계산이 두 군데에 흩어져 있다**

```java
int half = (maxH + minH) / 2;   // 루프 전
while (minH <= maxH) {
    ...
    half = (maxH + minH) / 2;   // 루프 끝
}
```

같은 식이 두 번 나오면 한쪽만 고치는 실수가 생긴다. 루프 맨 앞으로 옮기면 한 줄로 끝난다.

```java
while (minH <= maxH) {
    int half = minH + (maxH - minH) / 2;   // 오버플로도 함께 예방
    ...
}
```

`minH + (maxH - minH) / 2`는 값이 같으면서 덧셈 오버플로가 없다. 이 문제엔 필요 없지만 **이분탐색 기본형으로 손에 붙여둘 것.**

**6. `else if (treeAmount < M)`은 그냥 `else`**

앞 조건이 `treeAmount >= M`이므로 남은 경우는 `< M`뿐이다. 조건을 한 번 더 쓰면 읽는 사람이 "어느 쪽도 아닌 경우가 있나?" 하고 멈칫하게 된다.

**7. `ans` 없이도 된다 (다만 지금 방식이 더 안전하다)**

루프가 끝나면 `maxH`가 곧 정답이다(`minH`는 실패한 첫 높이, `maxH = minH - 1`은 성공한 마지막 높이). 하지만 `ans`에 명시적으로 기록하는 지금 방식이 **경계 실수를 원천적으로 막아주므로**, 이분탐색이 완전히 익숙해지기 전까지는 이 습관을 유지하는 쪽을 권한다.

## 8. 배운 것

**"최댓값을 구하라"를 "이 값이 가능한가?"로 뒤집었을 때 답이 `OOO...XXX` 모양이면, 그 경계를 이분탐색으로 찾는다.**

이게 파라메트릭 서치의 전부다. 체크리스트는 세 개뿐이다.

1. **검사 함수가 있는가** — `H` 하나를 주면 가능/불가능을 `O(N)` 정도로 판정할 수 있는가.
2. **단조성이 있는가** — `H`가 커지면 무조건 불리해지는가(또는 그 반대인가). 여기서는 `total(H)`가 단조 감소.
3. **탐색 공간이 답의 범위인가** — 배열 원소가 아니라 `0 ~ 10^9`을 쪼갠다. 그래서 `N`이 아무리 커도 반복은 30회.

곁들여 얻은 것 세 가지:

- **이분탐색의 종료는 구간이 책임져야 한다. `break`에 맡기면 실패가 오답이 아니라 무한 루프로 나온다.** 표준형 `while (lo <= hi)` + `lo = mid + 1` / `hi = mid - 1`은 매 반복마다 구간이 **반드시** 줄어들므로 종료가 구조적으로 보장된다. 시도 1처럼 `maxH = half`로 두고 루프 조건을 `||`로 엮으면 이 보장이 사라진다(→ 6번). 조건식을 쓸 때 **"이 식이 거짓이 되는 상태가 존재하는가"**를 한 번 확인하는 습관이 필요하다.
- **"정확히 M"이 아니라 "적어도 M"이면 `>=`로 묶고 성공한 값을 기록한다.** 등호를 종료 조건으로 쓰면 `M`을 딱 맞추는 값이 없는 입력에서 답을 놓친다. `4 6 / 20 15 10 17`이 그 반례다.
- **최적화를 넣었으면 실제로 이득인지 재본다.** 이번 정렬처럼 "조기 종료되니까 빠르겠지"가 실측에서는 110ms 손해로 나오는 경우가 있다. `O(N log N)` 한 번과 `O(N)` 30번은 같은 자릿수라, 상수 비교는 감이 아니라 측정으로 판단해야 한다.
