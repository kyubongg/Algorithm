## 1. 문제

울타리로 나뉜 `R × C` 마당에 양과 늑대가 흩어져 있다. **울타리를 넘지 않고 상하좌우로 오갈 수 있는 칸들이 하나의 영역**이고, 영역마다 싸움이 벌어진다.

- 영역 안의 **양 > 늑대**면 양이 이겨서 늑대를 전부 쫓아낸다.
- 그렇지 않으면(**늑대 ≥ 양**) 늑대가 그 영역의 양을 전부 먹는다.

아침까지 살아남은 양과 늑대의 총 수를 출력한다.

### 입력

```
첫 줄     R C      (마당의 행, 열)
다음 R줄  C개의 글자   '.' 빈 필드 / '#' 울타리 / 'o' 양 / 'v' 늑대
```

### 출력

살아남은 **양의 수와 늑대의 수**를 한 줄에 공백으로 구분해 출력한다. (양이 먼저다)

### 제한

- `3 ≤ R, C ≤ 250` → 최대 `62,500`칸
- 시간 1초 / 메모리 128MB
- 문제 본문의 두 가지 단서
  - "마당에서 **탈출**할 수 있는 칸은 어떤 영역에도 속하지 않는다"
  - "**맨 처음 모든 양과 늑대는 마당 안 영역에 존재한다**" ← 이 문장이 위 단서를 무력화한다 (2번 관찰)

### 예제

```
[입력]
6 6
...#..
.##v#.
#v.#.#
#.o#.#
.###.#
...###

[출력]
0 2
```

`(1,3)`의 늑대는 사방이 울타리라 **혼자 있는 영역**이고, `(2,1)`의 늑대와 `(3,2)`의 양은 **같은 영역에 1:1로 갇혀 있다.** 동수는 늑대 승이라 양이 먹히고, 늑대 두 마리가 살아남는다. **예제 1이 이미 동점 판정을 시험하고 있다** — 6번에서 이게 왜 중요한지 나온다.

```
[입력]
8 8
.######.
#..o...#
#.####.#
#.#v.#.#
#.#.o#o#
#o.##..#
#.v..v.#
.######.

[출력]
3 1
```

```
[입력]
9 12
.###.#####..
#.oo#...#v#.
#..o#.#.#.#.
#..##o#...#.
#.#v#o###.#.
#..#v#....#.
#...v#v####.
.####.#vv.o#
.......####.

[출력]
3 5
```

## 2. 접근

### 관찰

- **문제 전체가 "연결 요소마다 개수 세기" 한 문장으로 줄어든다.** 격자를 그래프로 보면 `.`, `o`, `v`가 정점이고 `#`은 정점이 아니다. 구할 것은 각 연결 요소 안의 `o` 개수와 `v` 개수뿐이다. **탐색 경로도, 거리도, 순서도 쓰지 않는다** — 방문한 칸을 세기만 하면 된다.

- **영역끼리는 완전히 독립이다.** 어떤 영역의 승패가 다른 영역에 영향을 주지 않으므로, 한 영역을 다 훑고 나서 그 자리에서 승패를 확정하고 전역 누적값에 더한 뒤 잊어버려도 된다. 영역 목록을 따로 들고 있을 필요가 없다.

- **`isVisited`에 울타리를 미리 `true`로 박아두면 탐색 조건에서 `'#'` 검사가 사라진다.** 이 코드에서 제일 잘한 부분이다.

  ```java
  if (inputChar == '#') isVisited[r][c] = true;   // 입력 받을 때 한 번
  ...
  if (nr >= 0 && nr < R && nc >= 0 && nc < C && !isVisited[nr][nc])   // '#' 검사가 없다
  ```

  `isVisited`가 "이미 세었다"와 "애초에 셀 수 없다"를 **한 배열로 겸한다.** 덕분에 사방탐색 조건이 범위 검사 + 방문 검사만 남고, 바깥 이중 루프의 `if (!isVisited[r][c])`도 **"새 영역의 시작점"과 "울타리가 아님"을 동시에** 걸러낸다. 조건을 두 군데(시작점 판별 + 이웃 판별)에서 각각 안 써도 되니, `'#'` 검사를 한쪽에만 빼먹는 전형적인 실수가 구조적으로 불가능해진다.

- **동수는 늑대 승이다.** 문제는 "양의 수가 늑대의 수보다 **많다면**" 양이 이긴다고만 한다. 즉 참인 조건은 `양 > 늑대` 하나뿐이고 나머지는 전부 늑대 승이다.

  ```java
  if (nowWolf < nowSheep) sheep += nowSheep;   // 양 > 늑대
  else wolf += nowWolf;                        // 늑대 > 양, 늑대 == 양 을 한꺼번에
  ```

  `else` 하나가 "늑대가 더 많다"와 "동수다"를 같이 받는다. **부등호를 `<=`로 잘못 쓰면 예제 1부터 틀린다** (6번에서 재현).

- **"탈출할 수 있는 칸은 어떤 영역에도 속하지 않는다"는 문장은 구현할 필요가 없다.** 처음 읽을 때 제일 걸리는 문장인데, 바로 다음 줄의 "맨 처음 모든 양과 늑대는 마당 안 영역에 존재한다"가 이걸 지워준다. 탈출 가능한 영역(= 테두리에 닿는 열린 영역)에는 **동물이 하나도 없다는 게 보장**되므로, 그 영역을 그냥 평범한 영역처럼 탐색해도 `nowWolf = 0, nowSheep = 0`이 되고 `else` 분기로 들어가 `wolf += 0`이 된다. **아무 일도 일어나지 않는다.**

  문장 그대로 "테두리에 닿는 영역은 제외"까지 구현한 코드를 따로 짜서 비교했다.

  | 입력 | 지금 코드 | 탈출 영역 제외 구현 |
  | --- | --- | --- |
  | 예제 1 | `0 2` | `0 2` |
  | 예제 2 | `3 1` | `3 1` |
  | 예제 3 | `3 5` | `3 5` |
  | `3 3 / o.. / ... / ...` (보장 위반) | `1 0` | `0 0` |

  **보장이 지켜지는 한 두 구현은 항상 같다.** 마지막 줄은 문제가 주지 않겠다고 약속한 입력이라, 실제 채점에서는 나올 수 없다.

- **크기가 작다.** 최대 `250 × 250 = 62,500`칸이고 각 칸은 정확히 한 번만 큐에 들어간다. 이웃 검사가 `62,500 × 4 = 250,000`회. 1초 제한에서 **알고리즘은 논쟁거리가 아니다.** 실제로 탐색에 걸린 시간은 로컬 실측 14ms였다(4번). 채점 결과 475ms는 거의 전부 JVM 기동 시간이다.

- **재귀 DFS를 쓰면 안 되는 크기다.** 이게 이 문제에서 제일 중요한 판단이다 → 아래 알고리즘 선택.

### 아이디어

격자 전체를 왼쪽 위부터 훑으면서 아직 방문하지 않은 칸을 만나면, 그 칸을 시작점으로 BFS를 돌려 **그 칸이 속한 영역 전체를 한 번에 소진**한다. 소진하면서 만난 `o`와 `v`를 지역 변수에 세고, 큐가 비면 그 자리에서 승패를 판정해 전역 `sheep` / `wolf`에 더한다.

바깥 이중 루프는 `62,500`번 돌지만, 이미 방문 처리된 칸은 즉시 건너뛰므로 **BFS가 실제로 시작되는 횟수는 영역 개수와 정확히 같다.**

### 알고리즘 선택

| 후보 | 가능 여부 | 채택 |
| --- | --- | --- |
| BFS (큐) | 큐 최대 길이 250 (실측). 재귀 없음 | **O** |
| 재귀 DFS | **250×250 전부 열린 마당에서 StackOverflowError** (실측: 깊이 7,824에서 사망) | X |
| 명시적 스택 DFS | 동작함. 스택 최대 깊이도 안전 | △: BFS와 차이 없음, 굳이 바꿀 이유 없음 |
| 유니온 파인드 | `62,500`개 원소로 가능 | X: 영역별 집계를 위해 루트별 카운터를 또 들어야 해서 더 번거롭다 |

**재귀 DFS 탈락 근거 (직접 재현)**

같은 로직을 재귀로 짜서 `250 × 250` 전부 `.`인 입력에 돌렸다.

```
$ java Dfs < big_open.txt
Exception in thread "main" java.lang.StackOverflowError
    at Dfs.dfs(Dfs.java:23)
    at Dfs.dfs(Dfs.java:23)
    ...

$ java -Xss64m Dfs < big_open.txt     # 스택을 64MB로 키우면
최대 재귀 깊이: 62500
0 0
```

| 입력 (250×250) | 재귀 DFS 결과 | BFS 큐 최대 길이 |
| --- | --- | --- |
| 전부 열린 마당 | 깊이 약 **7,824**에서 StackOverflowError | **250** |
| 뱀 모양 미로 | 깊이 약 **7,816**에서 StackOverflowError | **1** |
| 무작위 (`.#ov` 혼합) | 깊이 약 **10,513**에서 StackOverflowError | **217** |
| 1칸짜리 영역 15,625개 | 완주 (최대 깊이 1) | 1 |

**격차가 크다.** 완주하려면 `62,500` 프레임이 필요한데 기본 스택으로는 8천 언저리에서 죽는다. 반면 BFS 큐는 **최대 250개**밖에 담기지 않는다 — BFS의 큐에는 "지금 경계선(프론티어)"만 들어가는데, 250×250 격자에서 그 경계선은 대각선 파면이라 길어야 250칸이기 때문이다. 뱀 모양 미로에서 큐 길이가 **1**인 것도 같은 이유다(폭이 1인 통로라 프론티어가 한 칸씩만 전진한다).

> 여기서 얻을 교훈: **DFS의 재귀 깊이는 영역의 칸 수만큼 커지지만, BFS의 큐 길이는 영역의 "둘레"만큼만 커진다.** 격자가 `250 × 250`을 넘어가면 재귀 DFS는 그 자체로 위험 요소다.

**자료구조**: `ArrayDeque<int[]>`. `LinkedList`와 달리 노드 객체를 매번 만들지 않고, `Queue`로 쓸 때 `add`/`poll`이 상수 시간이라 적절한 선택이다. 다만 좌표를 `int[]`로 감싸는 것과 영역마다 새 `ArrayDeque`를 만드는 것은 각각 비용이 있다 → 7번에서 실측으로 따진다.

## 3. 설계

### 동작 순서

```
1. R, C 입력
2. map[R][C], isVisited[R][C] 준비
3. R개 줄을 읽으며:
   3-1. map[r][c] = 글자
   3-2. 글자가 '#'이면 isVisited[r][c] = true       // 울타리 = 미리 방문 처리
4. sheep = 0, wolf = 0
5. 모든 칸 (r, c)에 대해:
   5-1. isVisited[r][c]가 false이면 → 새 영역의 시작점이다. BFS 시작
6. BFS(시작 r, c):
   6-1. 큐 생성, (r,c) 삽입, isVisited[r][c] = true, 시작 칸의 동물을 센다
   6-2. 큐가 빌 때까지:
        - 하나 꺼내서 4방향을 본다
        - 범위 안 + 미방문이면 → 방문 처리 + 큐에 삽입 + 그 칸의 동물을 센다
   6-3. nowSheep > nowWolf 이면 sheep += nowSheep, 아니면 wolf += nowWolf
7. "sheep wolf" 출력
```

**6-2의 방문 처리 위치가 핵심이다.** `isVisited[nr][nc] = true`를 **큐에 넣는 그 순간**에 한다. 꺼낼 때로 미루면 같은 칸이 여러 번 큐에 들어가고, 그대로 세면 **한 마리를 여러 번 센다** — 6번에서 재현했다.

### 엣지 케이스

전부 로컬에서 직접 돌려 확인했다.

- **동물이 하나도 없는 마당** — `3 3 / ... / ... / ...` → `0 0`. 영역 하나에 `nowWolf = nowSheep = 0`이라 `else` 분기로 가서 `wolf += 0`. 검증 완료.
- **전부 울타리** — `3 3 / ### / ### / ###` → `0 0`. 모든 칸이 처음부터 `isVisited = true`라 BFS가 **한 번도 시작되지 않는다.** 검증 완료.
- **동수 (양 1 : 늑대 1)** — `3 3 / ### / #ov / ###` → `0 1`. 늑대 승. 검증 완료.
- **양이 한 마리 더 많은 경우** — `3 4 / #### / #oov / ####` → `2 0`. 양 승, 늑대는 쫓겨나 0. 검증 완료.
- **늑대만 있는 영역** — `3 3 / ### / #vv / ###` → `0 2`. 양이 0이라 `0 < 2`가 거짓, `else`로 간다. 검증 완료.
- **울타리가 하나도 없는 마당** — `3 3 / ovv / ... / ...` → `0 2`. 전체가 한 영역. 검증 완료.
- **250×250 전부 열린 마당** — 영역 1개, 칸 62,500개. `0 0`, 정상 종료. **재귀 DFS였다면 여기서 StackOverflowError였다.**
- **250×250에 1칸짜리 영역 15,625개** — `15625 0`. 영역이 최대로 쪼개진 경우로, BFS가 15,625번 시작된다. 정상. 검증 완료.
- **줄 길이가 C보다 짧은 경우** — `input.charAt(c)`가 그대로 터진다. 실제로 재현했다.

  ```
  $ printf '3 5\n.....\n.o.\n.....\n' | java Main
  Exception in thread "main" java.lang.StringIndexOutOfBoundsException
      at java.base/java.lang.String.charAt(String.java:1517)
      at Main.main(Main.java:24)
  ```

  정상 입력에서는 생기지 않지만, 격자 문제에서 줄 끝 공백이 잘려 들어오는 사이트가 있다는 건 기억해둘 것.

### 무작위 교차 검증

예제 3개만 맞춰보고 넘어가지 않으려고, 이 문제를 **다른 방식으로 푼 참조 구현**(파이썬 / 울타리를 미리 방문 처리하지 않고 `g[nr][nc] != '#'`을 매번 직접 검사)을 따로 짜서 대조했다.

```
무작위 200,000건 (R, C = 3~7, '.#ov' 비율을 네 가지로 섞음)
→ 불일치 0건
```

비율을 바꾼 이유는 한 가지 모양에만 쏠리지 않게 하기 위해서다 — 울타리가 많아 영역이 잘게 쪼개진 격자, 울타리가 거의 없어 한 덩어리인 격자, 동물이 빽빽한 격자를 모두 섞었다.

## 4. 복잡도

| 구분 | 복잡도 | 근거 |
| --- | --- | --- |
| 시간 | O(R × C) | 각 칸은 정확히 한 번 큐에 들어가고 한 번 꺼내진다. `62,500`칸 × 이웃 4방향 = `250,000`회 검사. 제한 1초에 압도적 여유 |
| 공간 | O(R × C) | `char[250][250]` ≈ 129KB + `boolean[250][250]` ≈ 66KB. 큐는 최대 250개(실측). 제한 128MB |

바깥 이중 루프가 `62,500`번 도는 것과 BFS가 `62,500`칸을 처리하는 것을 **더해도** `O(R × C)`다. 루프는 이미 방문한 칸을 `if` 한 번으로 건너뛸 뿐이고, BFS가 실제로 시작되는 횟수는 영역 개수(최대 15,625개)와 같다.

### 실측 (로컬 JDK 17, 250 × 250, JIT 워밍업 없는 단발 실행)

제출 환경과 같은 조건으로 단계를 나눠 재봤다.

| 입력 (250×250) | 영역 수 | 입력 파싱 | BFS | `int[]` 할당 개수 | BFS 단계 할당량 |
| --- | --- | --- | --- | --- | --- |
| 전부 열린 마당 | 1 | 6.5 ms | 14.4 ms | 62,500 | 1.44 MB |
| 전부 양 | 1 | 6.9 ms | 13.1 ms | 62,500 | — |
| 1칸 영역 15,625개 | 15,625 | 6.3 ms | 4.5 ms | 15,625 | **2.03 MB** |
| 뱀 모양 미로 | 1 | 8.0 ms | 12.8 ms | 31,375 | — |
| 무작위 혼합 | 464 | 8.3 ms | 18.1 ms | 43,726 | 1.05 MB |

전체 실행 시간(JVM 기동 포함)은 로컬에서 `147 ~ 169 ms`였고, 아무 일도 안 하는 `Hello` 클래스가 `92 ~ 103 ms`였다.

읽는 방법이 세 가지다.

- **알고리즘은 전혀 문제가 아니다.** 실제 계산은 파싱 8ms + 탐색 18ms = 26ms이고, 나머지 120ms는 JVM 기동이다. 채점 결과 475ms도 같은 구조로 보면 된다 — 제출 시간의 대부분은 내 코드가 아니라 JVM이 쓴 것이다.
- **1칸 영역 15,625개짜리 입력이 흥미롭다.** 칸 수는 같은데 탐색은 제일 빠르고(4.5ms), 할당량은 제일 많다(2.03MB). **영역마다 `new ArrayDeque<>()`를 만드는 비용**이 드러난 것이다. `ArrayDeque` 하나가 내부 `Object[16]`을 같이 달고 태어나므로 영역이 잘게 쪼개질수록 손해다 → 7번.
- **`int[]` 할당 62,500개는 전부 쓰레기다.** 큐에 동시에 들어있는 건 최대 250개인데(2번 실측) 62,500개를 만든다. 즉 만들어진 즉시 버려지는 객체가 1.44MB어치다. 제출 메모리 36.9MB는 JVM 기본값이 거의 전부이고 이 1.4MB는 그 안에 묻히지만, **"쓰지도 않을 객체를 칸 수만큼 만든다"는 사실 자체**는 짚고 가야 한다.

## 5. 코드

```java
import java.io.*;
import java.util.*;

public class Main {

    static char[][] map;
    static boolean[][] isVisited;
    static int R, C, wolf, sheep;
    static int[][] drc = {{0, -1}, {0, 1}, {-1, 0}, {1, 0}};
    public static void main(String[] args) throws Exception{

        BufferedReader br = new BufferedReader(new InputStreamReader(System.in));
        StringTokenizer st = new StringTokenizer(br.readLine());

        R = Integer.parseInt(st.nextToken());
        C = Integer.parseInt(st.nextToken());

        map = new char[R][C];
        isVisited = new boolean[R][C];

        for (int r = 0; r < R; r++) {
            String input = br.readLine();
            for (int c = 0; c < C; c++) {
                char inputChar = input.charAt(c);
                if (inputChar == '#') isVisited[r][c] = true;

                map[r][c] = inputChar;
            }
        }

        /**
         * '.': 빈 필드
         * '#': 울타리
         * 'o': 양, 'v': 늑대
         *
         *  한칸에서 수평/수직으로만 이동하면 울타리를 지나지 않는다면 두 칸은 같은 영역이라고 판단
         *
         *  양 vs 늑대 했을 때 수가 더 많은쪽이 이긴다.
         *
         *  R, C는 3 이상 250 이하
         */
        wolf = 0; sheep = 0;

        for (int r = 0; r < R; r++) {
            for (int c = 0; c < C; c++) {
                if (!isVisited[r][c]) {
                    getCountInArea(r, c, 0, 0);
                }
            }
        }

        System.out.println(sheep + " " + wolf);

    }

    /**
     * bfs 사용
     *
     * 1. isVisited 배열에서 '#'은 미리 true로 만든다.
     * 2. isVisited 배열을 순회하면서 false인 칸을 찾는다.
     *  2-1. false라면 영역 탐색 시작 (Queue를 이용)
     *   2-1-1. 영역 내부의 양, 늑대 수를 count
     *   2-1-2. 영역 탐색이 끝났을 때 숫자가 더 많은 동물의 수를 각자에 맞게 더한다.
     *
     * @param r: 현재 행
     * @param c: 현재 열
     * @param wolf: 현재 영역의 늑대 수
     * @param sheep: 현재 영역의 양 수
     */
    static void getCountInArea(int r, int c, int nowWolf, int nowSheep) {
//        System.out.println(r + ", " + c + ": " + nowWolf + " " + nowSheep);
        // bfs 알고리즘을 사용하기 위해 Queue를 이용해 사방탐색을 함.
        Queue<int[]> queue = new ArrayDeque<>();

        // 시작 칸 방문처리 및 queue에 삽입
        queue.add(new int[] {r,c});
        isVisited[r][c] = true;

        if (map[r][c] == 'v') nowWolf++;
        else if (map[r][c] == 'o') nowSheep++;

        while (!queue.isEmpty()) {
            int[] arr = queue.poll();

            for (int i = 0; i < 4; i++) {
                int nr = arr[0] + drc[i][0];
                int nc = arr[1] + drc[i][1];


                // nr, nc가 map 영역 내부이고 방문한 곳이 아니라면 진행
                if (nr >= 0 && nr < R && nc >= 0 && nc < C && !isVisited[nr][nc]) {
                    isVisited[nr][nc] = true;
                    queue.add(new int[] {nr, nc});

                    if (map[nr][nc] == 'v') nowWolf++;
                    else if (map[nr][nc] == 'o') nowSheep++;
                }
            }
        }


        if (nowWolf < nowSheep) sheep += nowSheep;
        else wolf += nowWolf;

    }
}
```

## 6. 삽질 기록

| 시도 | 결과 | 원인 | 고친 것 |
| --- | --- | --- | --- |
| 1 | 통과 | | |

제출 과정에서 틀린 기록은 남아 있지 않다. 대신 **이 코드가 (의도했든 아니든) 피해간 함정 두 개**를 직접 코드로 만들어 돌려봤다. 둘 다 격자 BFS에서 반복해서 나오는 실수이고, 다음에 비슷한 문제를 풀 때 확인할 지점이다.

### 함정 A — 방문 처리를 "꺼낼 때" 하면

지금 코드는 **큐에 넣는 순간** `isVisited[nr][nc] = true`를 한다. 이걸 꺼낼 때로 미룬 변형을 만들어 돌렸다.

**(A-1) 꺼낼 때 방문 처리 + 꺼낼 때 재확인 없음** — 답이 틀린다.

```java
while (!queue.isEmpty()) {
    int[] x = queue.poll();
    isVisited[x[0]][x[1]] = true;          // 여기서 처음 방문 처리
    if (map[x[0]][x[1]] == 'v') nowWolf++;  // ← 같은 칸을 여러 번 센다
    ...
}
```

| 입력 | A-1의 출력 | 정답 |
| --- | --- | --- |
| 예제 1 | `2 1` | `0 2` |
| 예제 2 | `2 4` | `3 1` |
| 예제 3 | `5 5` | `3 5` |

한 칸이 이웃 여러 곳에서 동시에 큐에 들어가므로 **동물이 중복으로 세어진다.** 예제 1이 `2 1`이 되는 게 특히 고약한데, 양 1마리가 2로 부풀어 `2 > 1`이 되면서 **승패까지 뒤집힌다.** 개수가 조금 틀리는 게 아니라 답의 방향이 바뀐다.

**(A-2) 꺼낼 때 방문 처리 + 꺼낼 때 `if (isVisited) continue;` 재확인** — 답은 맞지만 낭비다.

```
250 × 250 전부 열린 마당
정상 코드 : 큐 삽입 62,500회, 큐 최대 길이 250
A-2      : 큐 삽입 124,501회, 큐 최대 길이 499
```

**정확히 2배다.** 답은 맞으므로 채점에서는 통과하지만, 삽입할 때 한 줄로 막을 수 있는 걸 꺼낼 때 걸러내느라 객체를 두 배로 만든다. **BFS에서 방문 처리는 큐에 넣는 시점에 한다** — 이유가 "관례"가 아니라 이 숫자다.

### 함정 B — 동점 판정의 부등호

`if (nowWolf < nowSheep)`를 `if (nowWolf <= nowSheep)`로 쓰면(= 동수일 때 양이 이긴다고 착각하면) 이렇게 된다.

| 입력 | B의 출력 | 정답 |
| --- | --- | --- |
| 예제 1 | `1 1` | `0 2` |
| 예제 2 | `4 0` | `3 1` |
| 예제 3 | `5 3` | `3 5` |

**예제 세 개가 모두 틀린다.** 다행히 이 함정은 제출 전에 예제만 돌려봐도 걸린다 — 문제가 예제 1에 1:1 동점 영역을 일부러 넣어뒀기 때문이다(1번 참고). 반대로 말하면 **"많다면"이라는 한 단어를 `>`로 옮길 때 등호를 붙일지 말지를 문제 문장에서 확인해야 한다.** 이 문제는 양에게 불리한 쪽(등호 없음)이다.

## 7. 개선할 점

**1. `nowWolf`, `nowSheep` 파라미터는 죽은 인자다**

```java
getCountInArea(r, c, 0, 0);                              // 호출부는 항상 0, 0
static void getCountInArea(int r, int c, int nowWolf, int nowSheep)
```

호출이 한 군데뿐이고 항상 `0, 0`을 넘긴다. 재귀 DFS를 염두에 두고 만든 시그니처가 BFS로 바꾸는 과정에서 남은 것으로 보인다. **BFS는 큐가 재귀를 대신하므로 누적값을 인자로 나를 이유가 없다.** 메서드 안에서 `int nowWolf = 0, nowSheep = 0;`으로 선언하면 시그니처가 짧아지고, 읽는 사람이 "0이 아닌 값이 들어오는 호출이 어딘가 있나?" 하고 찾을 일도 없다.

```java
static void getCountInArea(int r, int c) {
    int nowWolf = 0, nowSheep = 0;
    ...
}
```

주석의 `@param wolf` / `@param sheep`도 실제 파라미터 이름(`nowWolf` / `nowSheep`)과 어긋나 있다. 파라미터를 없애면 이 불일치도 같이 사라진다.

**2. 시작 칸을 세는 코드가 따로 떨어져 있다**

지금은 동물을 세는 코드가 **두 군데**다.

```java
if (map[r][c] == 'v') nowWolf++;              // 시작 칸용 (while문 밖)
else if (map[r][c] == 'o') nowSheep++;
...
    if (map[nr][nc] == 'v') nowWolf++;        // 이웃 칸용 (while문 안)
    else if (map[nr][nc] == 'o') nowSheep++;
```

시작 칸만 큐 밖에서 처리하니 같은 로직이 복사돼 있다. **꺼낼 때 세면 한 군데로 합쳐진다.** 방문 처리는 여전히 넣을 때 하고(함정 A), 세는 것만 꺼낼 때로 옮기면 된다 — 둘은 별개다.

```java
while (head < tail) {
    int cur = queue[head++];
    if (map[cur] == 'o') nowSheep++;          // 모든 칸이 여기 한 번씩만 온다
    else if (map[cur] == 'v') nowWolf++;
    ...
}
```

로직이 두 벌이면 한쪽만 고치는 사고가 난다. 실제로 **함정 B의 부등호를 고칠 때도, 새 규칙을 추가할 때도 두 곳을 같이 봐야 한다.**

**3. 좌표를 `int[]`로 감싸지 말고 `int` 하나로 인코딩하기**

`new int[]{nr, nc}`가 칸마다 하나씩, 250×250이면 **62,500개** 만들어진다(4번 실측, 1.44MB). 그런데 큐에 동시에 들어있는 건 **최대 250개**다. 만들자마자 버려지는 객체가 대부분이다.

`(r, c)`는 `r * C + c`라는 **정수 하나**로 완전히 표현된다. 그러면 큐가 `int[]` 한 개면 되고, 각 칸이 딱 한 번 들어가므로 **길이 `R * C`짜리 배열 하나를 미리 잡아두면 절대 넘치지 않는다.**

**4. 영역마다 `new ArrayDeque<>()`를 만들지 말고 큐 하나를 재사용하기**

영역이 잘게 쪼개진 입력(1칸짜리 영역 15,625개)에서 BFS 단계 할당량이 **2.03MB로 제일 컸다.** 칸 수는 다른 입력과 똑같은데 말이다. `ArrayDeque` 하나가 내부 `Object[16]`을 달고 태어나므로, **1칸을 탐색하려고 16칸짜리 배열을 만들고 버리는 일**이 15,625번 반복된 것이다.

3번과 4번을 합치면 이렇게 된다.

```java
int[] queue = new int[R * C];      // 큐 하나를 모든 영역에서 재사용
...
for (int start = 0; start < R * C; start++) {
    if (isVisited[start]) continue;

    int head = 0, tail = 0, nowSheep = 0, nowWolf = 0;   // 인덱스만 초기화
    queue[tail++] = start;
    isVisited[start] = true;

    while (head < tail) {
        int cur = queue[head++];
        if (map[cur] == 'o') nowSheep++;
        else if (map[cur] == 'v') nowWolf++;

        int r = cur / C, c = cur - r * C;
        if (c > 0     && !isVisited[cur - 1]) { isVisited[cur - 1] = true; queue[tail++] = cur - 1; }
        if (c < C - 1 && !isVisited[cur + 1]) { isVisited[cur + 1] = true; queue[tail++] = cur + 1; }
        if (r > 0     && !isVisited[cur - C]) { isVisited[cur - C] = true; queue[tail++] = cur - C; }
        if (r < R - 1 && !isVisited[cur + C]) { isVisited[cur + C] = true; queue[tail++] = cur + C; }
    }

    if (nowSheep > nowWolf) sheep += nowSheep;
    else wolf += nowWolf;
}
```

`head`/`tail`을 영역마다 0으로 되돌리기만 하면 되므로 배열을 지울 필요도 없다. 무작위 200,000건에서 원본과 **출력이 100% 동일**한 것을 확인했다.

| 입력 (250×250) | 원본 BFS | 개선판 BFS |
| --- | --- | --- |
| 전부 열린 마당 | 14.4 ms | **4.1 ms** |
| 무작위 혼합 | 18.1 ms | **5.5 ms** |
| 1칸 영역 15,625개 | 4.5 ms | **2.0 ms** |
| 뱀 모양 미로 | 12.8 ms | **2.9 ms** |

탐색 단계만 보면 **3배 이상 빠르다.** 다만 전체 실행 시간은 `147~169ms → 136~153ms` 정도로만 줄었다. **JVM 기동이 대부분이라 알고리즘 개선이 눈에 띄지 않는다** — 그래서 이건 "통과하려고" 하는 개선이 아니라 습관을 들이려고 하는 개선이다.

> 한 가지 대가는 있다. `cur / C`, `cur - r * C`로 좌표를 되살리는 코드와 `c > 0`, `c < C - 1` 같은 경계 검사가 `drc` 루프보다 읽기 어렵다. **격자가 커서 할당이 실제로 문제가 될 때만 쓸 것.** 이 문제 크기(62,500칸)에서는 원본으로도 충분하다.

**5. 입력 파싱**

지금 방식이 26ms 중 7ms를 쓴다. 세 가지를 재봤다.

| 방식 | 파싱 시간 (250×250) |
| --- | --- |
| `charAt`으로 한 글자씩 (현재) | 6.7 ~ 7.0 ms |
| `line.toCharArray()`로 줄 단위 | 5.3 ~ 5.4 ms |
| `System.in.readAllBytes()`로 통째 | **1.5 ~ 1.7 ms** |

`toCharArray()`는 한 줄로 바꿀 수 있어서 값이 싸다.

```java
map[r] = br.readLine().toCharArray();
for (int c = 0; c < C; c++) if (map[r][c] == '#') isVisited[r][c] = true;
```

`readAllBytes` 방식은 4배 빠르지만 격자 문제에서 개행(`\n` / `\r\n`)을 손으로 건너뛰어야 해서 코드가 늘어난다. **전체 150ms 중 5ms를 아끼는 일**이라 이 문제에서는 의미가 없고, 격자가 `1000 × 1000` 이상인 문제에서 꺼내 쓸 카드다.

**6. `map`을 `char[][]`가 아니라 `byte[][]`로**

`char`는 2바이트라 `250 × 250`이 약 129KB를 쓴다. 어차피 다루는 글자가 ASCII 네 종류(`.`, `#`, `o`, `v`)뿐이므로 `byte[][]`면 절반이다. 메모리 제한 128MB에서는 아무 의미 없는 절약이지만, 5번의 `readAllBytes` 방식과는 자연스럽게 맞물린다(바이트를 `char`로 변환하는 단계가 사라진다).

**7. 디버그용 주석 정리**

`getCountInArea` 첫 줄의 주석 처리된 `System.out.println`은 제출 전에 지우는 편이 낫다. 남겨두면 다음에 이 파일을 열었을 때 "이걸 왜 껐지?"부터 읽게 된다.

## 8. 배운 것

**격자 문제에서 재귀 DFS는 격자 크기를 먼저 확인하고 골라야 한다.** 이 문제는 `250 × 250 = 62,500`칸이라 재귀 DFS가 **기본 스택으로 깊이 8천 언저리에서 죽는다**(6번 아래 실측). 반면 BFS 큐는 최대 250개만 담았다. 차이가 나는 이유는 분명하다 — **DFS 스택은 "지금까지 지나온 경로 전체"를 들고 있고, BFS 큐는 "지금 경계선"만 들고 있다.** 경로는 칸 수만큼 길어질 수 있지만 경계선은 격자의 한 변 정도다. 격자가 `100 × 100`을 넘어가면 재귀 대신 큐를 쓰거나 명시적 스택으로 바꿀 것.

**방문 처리는 큐에 넣는 시점에 한다.** 꺼낼 때로 미루면 (재확인을 빼먹으면) 같은 칸을 여러 번 세어 **답의 방향까지 뒤집히고**(예제 1에서 양 1마리가 2마리가 되어 늑대를 이겼다), 재확인을 넣어도 큐 삽입이 정확히 2배가 된다. 두 경우 다 직접 재현해서 숫자로 확인했다.

**`isVisited`에 "갈 수 없는 칸"을 미리 심어두면 탐색 조건이 짧아진다.** 벽/장애물을 입력 받을 때 방문 처리해버리면 사방탐색 조건에서 벽 검사가 통째로 빠지고, 바깥 루프의 시작점 판별도 같은 배열 하나로 끝난다. **조건을 한 곳에만 두면 한쪽에만 빼먹는 실수가 구조적으로 불가능해진다.** 이 습관은 미로/섬/영역 문제 전반에 그대로 쓴다.

**"많다면"에 등호를 붙일지는 문제 문장에서 확인한다.** 이 문제는 `양 > 늑대`일 때만 양이 이기고 동수는 늑대 승이다. `else` 하나로 "늑대가 더 많다"와 "동수다"를 같이 받는 게 맞는데, 여기서 등호를 잘못 옮기면 예제 세 개가 전부 틀린다. **문제가 예제 1에 1:1 동점 영역을 넣어둔 건 우연이 아니다** — 출제자가 이 지점을 시험하고 있다.

**문제 본문의 예외 조항이 다른 문장에 의해 무력화되는 경우가 있다.** "탈출 가능한 칸은 어떤 영역에도 속하지 않는다"를 구현하려다 보면 테두리 판정을 넣게 되는데, 바로 다음 문장의 "모든 동물은 마당 안 영역에 존재한다"가 그걸 불필요하게 만든다. 두 구현을 다 짜서 비교해보니 **보장이 지켜지는 한 결과가 항상 같았다.** 제약 조건은 "무엇을 해야 하는가"뿐 아니라 **"무엇을 안 해도 되는가"**도 알려준다 — [예산](../2581.%20예산/README.md)에서 탐색 범위를 잘 잡아 규칙 (1)/(2) 분기가 사라졌던 것과 같은 종류의 이득이다.
