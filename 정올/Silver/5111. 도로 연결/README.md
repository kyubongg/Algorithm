> 난이도는 정올에 표기가 없고 **동일한 백준 문제를 찾지 못했다.** 다른 문제들처럼 solved.ac 티어를 빌려올 수가 없어서, 비슷한 유형(그리디 + 간단한 교환 논증)에 맞춰 **내가 실버 II로 어림잡은 값**이다. 근거가 있는 숫자가 아니니 나중에 출처를 찾으면 고칠 것.

## 1. 문제

친구 `N`명이 각자 다른 방에 있고, `i`번째 친구는 길이 `d[i]`짜리 트랙을 무한히 갖고 있다.
친구 `a`의 방과 `b`의 방을 도로로 이으면 그 도로의 길이는 **`d[a] + d[b]`** 이다.

**모든 방이 서로 오갈 수 있게** 도로를 놓을 때, 도로 길이 총합의 최솟값을 구한다.

> 문제 본문의 "i번째 친구가 갖고 있는 트랙의 길이는 모두 **i**로 동일하다"는 오타로 보인다. 그 뒤 문장과 제약 조건이 전부 `d[i]`를 쓰고 있고, 길이가 `i`로 고정이라면 입력으로 `d`를 받을 이유가 없다. **`i`번째 친구의 트랙 길이가 `d[i]`** 로 읽는 게 맞다.

### 입력

```
첫 줄     N        (친구 수 = 방 수)
둘째 줄   d[1] ... d[N]   (공백으로 구분)
```

> 정올 문제 페이지에 입력 형식이 따로 명시돼 있지 않아 **제출이 통과한 사실로부터 역으로 확인한 형식**이다. 둘째 줄에 `N`개가 한 줄로 온다는 가정에 의존하고 있고, 이게 3번 엣지 케이스와 6번 함정 B로 이어진다.

### 출력

모든 방을 연결하는 도로 길이 총합의 최솟값을 한 줄에 출력한다.

### 제한

- `1 ≤ N ≤ 100,000`
- `1 ≤ d[i] ≤ 10^9`
- 시간 1초 / 메모리 512MB

### 서브태스크

| # | 배점 | 추가 조건 | 이 풀이에서의 의미 |
| --- | --- | --- | --- |
| 1 | 20 | `d[1] = d[2] = ... = d[N]` | 답이 `(2N-2)·d`로 고정. 공식이 자동으로 맞는다 |
| 2 | 40 | `N ≤ 1,000` | `O(N^2)` 프림이 통과하는 구간 (100만 회) |
| 3 | 40 | 없음 | `N = 100,000`. **간선을 만드는 순간 끝난다** (아래 2번) |

### 예제

문제 본문에 예제가 같이 오지 않아서, **직접 만들어 돌려본 입력**을 적는다.

```
[입력]
4
1 3 5 7

[출력]
18
```

가장 짧은 트랙을 가진 1번(`d=1`)을 중심으로 나머지를 전부 붙인다.
`(1+3) + (1+5) + (1+7) = 18`.

```
[입력]
1
7

[출력]
0
```

방이 하나면 이을 도로가 없다. **`N = 1`은 반드시 확인해야 하는 입력이다** (3번).

## 2. 접근

### 관찰

- **간선을 만들면 안 된다.** 모든 방 쌍을 이을 수 있으므로 그래프는 완전그래프다. `N = 100,000`이면 간선이 `N(N-1)/2 ≈ 5 × 10^9`개다. **크루스칼은 간선을 정렬해야 하니 시작도 못 하고**, 메모리부터 터진다. 서브태스크 3이 노리는 지점이 정확히 이것이다. 즉 이 문제는 "MST를 구하는 문제"지만 **MST 알고리즘을 쓰면 틀리는 문제**다.

- **트리의 비용은 차수만으로 결정된다.** 이게 이 문제의 전부다. 어떤 스패닝 트리 `T`를 잡아도

  ```
  비용(T) = Σ (d[a] + d[b])  =  Σ  deg(i) · d[i]
           (a,b) ∈ T             i
  ```

  간선 하나가 양 끝 정점의 값을 한 번씩 더하므로, **각 정점 값은 자기 차수만큼 곱해진다.** 간선이 어디에 붙었는지는 사라지고 **차수 수열만 남는다.**

- **차수 수열에 걸린 조건은 딱 두 개다.** 스패닝 트리는 간선이 `N-1`개이므로

  ```
  Σ deg(i) = 2(N-1),    모든 i에 대해 deg(i) ≥ 1
  ```

  그러면 문제가 이렇게 바뀐다 — **합이 `2(N-1)`이고 각 항이 1 이상인 정수 수열로 `Σ deg(i)·d[i]`를 최소화하라.** 모두에게 1씩 나눠주면 `N`을 쓰고 **`2(N-1) - N = N-2`가 남는다.** 남은 `N-2`는 **`d`가 가장 작은 정점에 전부 몰아주는 게 최선**이다(1을 더 주는 비용이 곧 `d[i]`니까).

  ```
  최솟값 = Σ d[i] + (N-2) · min(d)
  ```

- **그 차수 수열은 실제로 만들 수 있다.** 최솟값 정점 하나가 차수 `N-1`, 나머지가 전부 차수 1 — **최솟값을 중심으로 한 별(star)** 이다. 하한이 실현 가능하므로 이게 답이다. 별의 비용을 직접 더해봐도 같다.

  ```
  (N-1)·min + (Σd - min) = Σd + (N-2)·min   ✔
  ```

- **`N = 1`에서도 공식이 그대로 맞는다.** `Σd + (1-2)·min = d[1] - d[1] = 0`. **분기를 따로 둘 필요가 없다** — 이건 운이 좋은 게 아니라 "간선 0개, 차수 합 0"이 식에 그대로 반영된 결과다.

- **정렬도 힙도 필요 없다.** 필요한 건 `Σd`와 `min(d)` 두 개뿐이다. **한 번 훑으면 끝난다.** 제출본은 우선순위 큐로 `N`개를 전부 정렬하는데, **꺼낸 순서를 어디에도 쓰지 않는다** (7번).

- **long이 필요하다.** 답의 최댓값은 `10^5 × 10^9 + 99,998 × 10^9 ≈ 2 × 10^14`로 int를 한참 넘는다. 제출본은 `long ans`를 써서 맞았고, **`int ans`였으면 `-1,447,105,536`이 나온다** (6번에서 재현).

- **`int min + int next`는 여유가 7.4%밖에 없다.** 간선 하나의 최대 무게는 `2 × 10^9`이고 `Integer.MAX_VALUE`는 `2,147,483,647`이다.

  ```
  max edge weight  d_a+d_b = 2000000000
  Integer.MAX_VALUE        = 2147483647
  margin                   = 147483647  (7.4%)
  ```

  **제약이 `10^9`이라서 간신히 맞은 것**이지 안전해서 맞은 게 아니다. 같은 코드에 `d ≤ 1.1 × 10^9`만 들어와도 `1100000000 + 1100000000 = -2094967296`이 된다.

### 아이디어

"가장 짧은 트랙을 가진 친구를 허브로 삼아 나머지를 전부 그 방에 붙인다." 제출본 주석의 `1 3 5 7 -> 1,3 연결 1,5 연결 1,7 연결`이 정확히 이 그림이고, **결론은 맞다.**

다만 거기서 한 발 더 갈 수 있었다. 허브가 정해지면 **더할 값들의 순서는 아무 의미가 없다.** `(min + 3) + (min + 5) + (min + 7)`이나 `(min + 7) + (min + 3) + (min + 5)`나 같은 수다. 그러니 **"작은 것부터 꺼낸다"는 우선순위 큐의 기능 자체가 이 문제에서 쓰이지 않는다.** 필요한 건 최솟값 하나와 총합 하나다.

### 알고리즘 선택

| 후보 | 가능 여부 | 채택 |
| --- | --- | --- |
| 크루스칼 | 간선 `5 × 10^9`개를 만들어 정렬해야 함 | X: 메모리/시간 모두 불가 |
| 프림 `O(N^2)` | `10^10`회. 서브태스크 2(`N ≤ 1,000`)까지만 통과 | X: 제출용으로는 탈락. **검증용으로는 씀** (3번) |
| 정렬 후 합 | `O(N log N)`. 동작함 | △: 정렬 결과를 안 쓴다 |
| 우선순위 큐 (제출본) | `O(N log N)`. 동작함 | △: **통과했지만 꺼낸 순서를 안 쓴다** |
| 최솟값 + 합 1패스 | `O(N)`, 추가 메모리 `O(1)` | **O** |

**자료구조**: 사실상 없다. `long sum`과 `long min` 두 변수면 된다. 배열조차 필요 없다 — **값을 보관할 이유가 없기 때문이다.** 제출본이 `PriorityQueue<Integer>`에 `Integer` 10만 개를 박스로 만들어 넣는 것과 대비된다(4번 실측에서 힙 사용량 `13.5MB` vs `1.8MB`).

## 3. 설계

### 동작 순서

```
1. N 입력
2. sum = 0, min = +무한
3. N번 반복:
   3-1. d 입력
   3-2. sum += d
   3-3. d < min 이면 min = d
4. sum + (N-2) * min 을 출력   // long으로 계산
```

**4번 줄의 `(N-2)`를 `(long)`으로 캐스팅해야 한다.** `(N-2)`와 `min`이 둘 다 int면 `99,998 × 10^9`이 int 곱셈으로 먼저 계산돼 터진다. `sum`이 long이라도 소용없다 — **곱셈이 덧셈보다 먼저 일어나기 때문이다.**

### 엣지 케이스

전부 로컬에서 직접 돌려 확인했다.

- **`N = 1`** — `1 / 7` → `0`. 공식이 `7 + (1-2)×7 = 0`을 준다. 제출본도 `pq.poll()`로 하나 꺼낸 뒤 `while`을 한 번도 안 돌아 `0`. **양쪽 다 검증 완료.**
- **`N = 2`** — `2 / 5 9` → `14`. 도로 하나. 공식이 `14 + 0 = 14`.
- **모두 같은 값 (서브태스크 1)** — `d`가 전부 `1000`, `N = 100,000` → `199,998,000`. `(2N-2)·d = 199,998 × 1000`과 일치. **검증 완료.**
- **전부 최댓값** — `d`가 전부 `10^9`, `N = 100,000` → `199,998,000,000,000`. **약 `2 × 10^14`로 long의 필요성이 드러나는 입력이다.** 이 입력이 `int ans` 버전을 죽인다(6번).
- **오름차순 / 내림차순** — 최솟값이 맨 앞/맨 뒤에 오는 경우. 둘 다 정답. 제출본은 **이 두 경우에서 힙 성능이 갈린다**(4번 표).
- **값이 여러 줄에 걸쳐 오는 경우** — `d`를 한 줄에 하나씩 주면 **제출본이 그대로 죽는다.**

  ```
  $ java Main < in_multi.txt
  Exception in thread "main" java.util.NoSuchElementException
      at java.base/java.util.StringTokenizer.nextToken(StringTokenizer.java:347)
      at Main.main(Main.java:13)
  ```

  정올의 실제 데이터는 한 줄이라 통과했지만, **`br.readLine()` 한 번으로 `N`개를 다 받는다는 건 검증되지 않은 가정이다.** 토큰 단위로 읽으면 이 가정 자체가 사라진다(7번).

- **CRLF 줄끝** — `3\r\n1 3 5\r\n` → `10`. `StringTokenizer`의 기본 구분자에 `\r`이 포함돼 있어 문제없다. 바이트 파싱 버전도 `'0'` 미만 문자를 전부 구분자로 보므로 동일하게 통과. **양쪽 다 검증 완료.**

### 교차 검증

공식 하나로 끝나는 풀이라 **"공식이 진짜 MST인가"가 이 문제의 전부**다. 예제 몇 개로는 불안해서 세 단계로 확인했다.

**(1) 모든 라벨 트리 전수 조사** — `n ≤ 8`이면 Prüfer 수열로 `n^(n-2)`개의 트리를 전부 만들 수 있다. 무작위 `d`에 대해 **전수 최소 비용**과 공식을 비교했다.

```
trials=2000 mismatch=0
  n=2 optimum-is-a-star 271/271
  n=3 optimum-is-a-star 286/286
  n=4 optimum-is-a-star 279/279
  n=5 optimum-is-a-star 295/295
  n=6 optimum-is-a-star 303/303
  n=7 optimum-is-a-star 271/271
  n=8 optimum-is-a-star 295/295
```

**최적 트리는 예외 없이 별 모양이었다.** 차수 논증이 말한 그대로다.

**(2) `O(N^2)` 프림과 대조** — 완전그래프에 진짜 MST 알고리즘을 돌려 공식과 비교했다.

| 설정 | 결과 |
| --- | --- |
| 20,000건, `N ≤ 60`, `d ≤ 30` (동점이 많이 생기는 조건) | mismatch 0 |
| 3,000건, `N ≤ 200`, `d ≤ 10^9` | mismatch 0 |
| 5,000건, `N ≤ 5`, `d ≤ 10^9` (작은 `N` 집중) | mismatch 0 |

`d ≤ 30`을 일부러 넣은 건 **최솟값이 여러 개일 때**(허브 후보가 여럿일 때)를 많이 만들기 위해서다.

**(3) 제출본 로직 vs 공식** — 제출한 우선순위 큐 로직과 공식을 같은 입력에 돌려 대조했다.

```
무작위 200,000건 (N = 1~12, d의 상한을 10^9 / 10^3 / 3 세 가지로 번갈아)
→ 불일치 0건
```

`d ≤ 3`짜리를 섞은 이유는 같다 — **중복값과 동점 상황을 강제로 많이 만들려고.** 이걸로 "제출본은 맞았고, 공식도 같은 답을 내며, 그 답이 진짜 MST"라는 사슬이 닫힌다.

## 4. 복잡도

| 구분 | 복잡도 | 근거 |
| --- | --- | --- |
| 시간 | **O(N)** | 값을 한 번씩만 본다. `10^5`회. 제한 1초에 사실상 무관 |
| 공간 | **O(1)** | `sum`, `min` 두 변수. 입력 버퍼 64KB 외에 아무것도 안 들고 있는다 |

제출본은 이렇다.

| 구분 | 복잡도 | 근거 |
| --- | --- | --- |
| 시간 | `O(N log N)` | `offer` `N`번 + `poll` `N`번, 각 `O(log N)` |
| 공간 | `O(N)` | `Integer` 박스 10만 개 + 내부 `Object[]` + 1.1MB짜리 입력 문자열 |

`O(N log N)`도 `N = 10^5`면 통과한다. **틀린 선택이 아니라 필요 없는 선택이다.** 얼마나 필요 없는지를 재봤다.

### 실측 (로컬 JDK 17, `N = 100,000`, 무작위 `d`, JIT 워밍업 없는 단발 실행)

| 방식 | 입력 읽기 | 계산 | 합계 | 종료 시 힙 |
| --- | --- | --- | --- | --- |
| **제출본** `BufferedReader` + `StringTokenizer` + `PriorityQueue` | 26 ms | offer 36 ms + poll 54 ms | **117 ms** | 13.5 MB |
| 큐만 제거 (`BR` + `ST` + 1패스) | 28 ms | 23 ms | **51 ms** | 10.0 MB |
| `StreamTokenizer` + 1패스 | 0.3 ms | 21 ms | **21 ms** | 1.8 MB |
| 바이트 직접 파싱 + 1패스 | 0.1 ms | 16 ms | **16 ms** | 1.8 MB |

전체 실행 시간(JVM 기동 포함, 15회 중 최솟값)도 같이 쟀다.

| | `N = 1` | `N = 100,000` | 차이 = 실제 작업 |
| --- | --- | --- | --- |
| 제출본 | 268 ms | 378 ms | **110 ms** |
| 바이트 파싱 1패스 | 267 ms | 275 ms | **8 ms** |

세 가지를 읽을 수 있다.

- **`N = 1`짜리 입력도 268ms가 걸린다.** 이게 이 환경의 JVM 기동 비용이다. **제출 결과 811ms 중 내 코드가 쓴 시간은 극히 일부**이고, 나머지는 JVM이 뜨는 시간 + 채점 서버의 IO다. 그래서 "811ms를 줄이겠다"는 목표는 애초에 잘못 잡은 목표다 — 줄일 수 있는 건 `110ms → 8ms` 구간뿐이다.
- **그래도 `110ms → 8ms`는 13배다.** 1초 제한에 여유가 있어서 티가 안 날 뿐, 같은 코드 습관을 `N`이 더 크거나 제한이 빡빡한 문제에 들고 가면 그대로 문제가 된다.
- **힙 13.5MB 중 대부분이 안 써도 되는 것이다.** `Integer` 10만 개(값이 `10^9`대라 `Integer` 캐시도 못 탄다)와 1.1MB짜리 입력 문자열. 제출 결과 54.8MB는 JVM 기본값이 대부분이지만, 그중 **10MB 이상이 내가 만든 쓰레기**라는 건 짚고 가야 한다.

### 힙은 입력 모양에 따라 4배까지 흔들린다

같은 `N = 100,000`인데 `poll` 구간만 떼어 재보면 이렇다.

| 입력 모양 | `offer` `N`번 | `poll` `N`번 | 합계 |
| --- | --- | --- | --- |
| 무작위 | 36 ms | **54 ms** | 118 ms |
| 전부 같은 값 (서브태스크 1) | 31 ms | **6 ms** | 54 ms |
| 전부 `10^9` | 30 ms | **4 ms** | 62 ms |
| 오름차순 | 31 ms | **38 ms** | 87 ms |
| 내림차순 | 37 ms | **23 ms** | 80 ms |

**값이 전부 같으면 `poll`이 9배 빨라진다.** `poll`은 마지막 원소를 루트에 올리고 아래로 내리는데, 모든 값이 같으면 **첫 비교에서 바로 멈춘다.** 반대로 무작위는 매번 `log N ≈ 17` 단계를 다 내려간다.

재밌는 건 **서브태스크 1(모두 같은 값)이 힙에게는 가장 쉬운 입력**이라는 점이다. 20점짜리 서브태스크가 "쉬운 조건"인 이유는 정답 공식이 단순해져서지, 실행이 빨라서가 아닌데 — 여기서는 우연히 둘 다 해당한다. **1패스 풀이는 이 표 전체가 필요 없다.** 입력 모양에 관계없이 항상 `O(N)`이다.

## 5. 코드

```java
import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;
import java.util.Arrays;
import java.util.PriorityQueue;
import java.util.StringTokenizer;

public class Main {

    public static void main(String[] args) throws IOException {
        BufferedReader br = new BufferedReader(new InputStreamReader(System.in));

        // i번째 친구가 들고 있는 트랙의 길이는 i이다.
        // a 와 b를 잇는 방법은 da + db이다

        // 모든 방이 연결되게 하는 도로 길이의 최솟값


        // 우선 순위 큐를 쓰면 되지 않을까
        // 1 3 5 7 -> 1,3 연결 1,5 연결 1,7 연결
        int N = Integer.parseInt(br.readLine());
        PriorityQueue<Integer> pq = new PriorityQueue<>();
        StringTokenizer st = new StringTokenizer(br.readLine());

        for (int i = 0; i < N; i++) {
            pq.add(Integer.parseInt(st.nextToken()));
        }

        int min = pq.poll();
        long ans = 0;
        while(!pq.isEmpty()) {
            int next = pq.poll();
            ans += min+next;
        }

        System.out.println(ans);
    }

}
```

| 시도 | 결과 | 원인 | 고친 것 |
| --- | --- | --- | --- |
| 1 | 통과 | | |

한 번에 통과했다. 대신 **이 코드가 아슬아슬하게 피해간 함정 세 개**를 직접 만들어 돌려봤다. 셋 다 "통과했으니 괜찮다"로 넘기면 다음 문제에서 그대로 밟을 것들이다.

### 함정 A — `long ans`를 `int ans`로 썼다면

제출본은 `long ans = 0`이다. 이걸 `int`로 바꾼 버전을 돌렸다.

| 입력 (`N = 100,000`) | `int ans` | 정답 |
| --- | --- | --- |
| 무작위 `d` | `-479810825` | `50083133827831` |
| `d`가 전부 `10^9` | `-1447105536` | `199998000000000` |

**음수가 나온다.** 답의 상한이 `2 × 10^14`니 당연한 결과인데, 중요한 건 **이게 예제로는 절대 안 걸린다**는 점이다. `4 / 1 3 5 7`은 `int`로도 `18`이 나온다. `long`을 쓸지는 **제약 조건의 곱셈으로 미리 계산해서 결정해야 하고**, 예제로 확인할 수 있는 종류의 것이 아니다.

### 함정 B — 입력이 한 줄이 아니었다면

`StringTokenizer st = new StringTokenizer(br.readLine())`은 **`N`개가 전부 둘째 줄 하나에 있다**고 가정한다.

```
$ java Main < in_multi.txt          # d를 한 줄에 하나씩
Exception in thread "main" java.util.NoSuchElementException
    at java.base/java.util.StringTokenizer.nextToken(StringTokenizer.java:347)
    at Main.main(Main.java:13)

$ printf '3 1 3 5\n' | java Main     # N과 d가 같은 줄
Exception in thread "main" java.lang.NumberFormatException: For input string: "3 1 3 5"
    at java.base/java.lang.Integer.parseInt(Integer.java:668)
```

같은 두 입력을 **토큰 단위로 읽는 버전**에 넣으면 각각 `50083133827831`, `10`이 정상 출력된다. 정올의 데이터가 한 줄이라 통과한 것이지, **코드가 입력 형식에 대해 옳았던 게 아니다.** `StreamTokenizer`나 바이트 파싱은 줄 개념 자체가 없어서 이 가정이 아예 필요 없어진다.

### 함정 C — `min + next`가 int 덧셈이다

```java
int min = pq.poll();
int next = pq.poll();
ans += min + next;        // int + int 를 계산한 뒤 long에 더한다
```

`ans`가 long이어도 **오른쪽 덧셈은 int로 먼저 계산된다.** 제약이 `d ≤ 10^9`이므로 최대 `2 × 10^9 < 2,147,483,647`로 **간신히 안전하다.** 여유는 `147,483,647`, 비율로 **7.4%.**

```
int 1.1e9 + 1.1e9 = -2094967296   <- 제약이 조금만 느슨했어도 터진다
```

**"통과했으니 맞다"와 "안전하다"는 다르다.** `ans += (long) min + next`처럼 한쪽만 long으로 올려두면 제약을 다시 확인할 일이 없어진다.

## 7. 개선할 점

**1. 우선순위 큐가 만드는 정보를 하나도 안 쓰고 있다**

이게 제일 큰 것이다. 힙은 **"작은 것부터 꺼내는 순서"** 를 제공하는 자료구조인데, 이 코드가 꺼낸 값으로 하는 일은 이것뿐이다.

```java
while (!pq.isEmpty()) {
    int next = pq.poll();
    ans += min + next;      // next를 그냥 더하기만 한다
}
```

**덧셈은 순서를 바꿔도 결과가 같다.** 즉 `poll`이 `log N`씩 써서 만들어낸 순서가 **다음 줄에서 즉시 버려진다.** 필요한 건 `min`과 `나머지의 합` 두 개뿐이고, 둘 다 한 번 훑으면 나온다.

```java
long sum = 0, min = Long.MAX_VALUE;
for (int i = 0; i < N; i++) {
    int d = nextInt();
    sum += d;
    if (d < min) min = d;
}
System.out.println(sum + (long)(N - 2) * min);
```

`offer 36ms + poll 54ms = 90ms`가 통째로 사라진다(4번 실측). **"자료구조가 만들어주는 걸 내가 쓰고 있나?"를 한 번 물어보면 걸러지는 종류의 과잉이다.**

**2. `(long)` 캐스팅 위치**

`sum + (N - 2) * min`을 그대로 쓰면 안 된다. `N - 2`와 `min`이 int면 `99,998 × 10^9`이 **int 곱셈으로 먼저 계산돼 오버플로우**한다. `sum`이 long이라 안전할 것 같지만, **곱셈이 덧셈보다 먼저 일어나므로 이미 늦었다.** `(long)(N - 2) * min`처럼 곱셈 자체를 long으로 올려야 한다. 위 코드에서 `min`을 `long`으로 선언한 것도 같은 이유다.

**3. 입력을 "줄"이 아니라 "토큰"으로 읽기**

함정 B가 사라지고, 1.1MB짜리 `String`을 만드는 비용(26ms)과 그 메모리도 같이 사라진다. 두 가지 선택지를 재봤다.

| 방식 | 입력 읽기 | 종료 시 힙 | 코드 길이 |
| --- | --- | --- | --- |
| `BufferedReader` + `StringTokenizer` (현재) | 26 ms | 10.0 MB | 짧다 |
| `StreamTokenizer` | 0.3 ms | 1.8 MB | 짧다 |
| 바이트 직접 파싱 | 0.1 ms | 1.8 MB | 길다 (헬퍼 필요) |

**`StreamTokenizer`가 비용 대비 이득이 제일 좋다.** 세 줄이면 되고 `nextInt` 헬퍼를 직접 짤 필요도 없다. 다만 값을 `double`(`nval`)로 받는다는 한계가 있는데, **`double`은 `2^53`까지 정수를 정확히 표현하므로 `10^9`은 안전하다** — 전부 `10^9`인 입력으로 확인해서 `199998000000000`이 정확히 나오는 걸 봤다. `10^15`를 넘는 값을 읽어야 하는 문제에서는 쓰면 안 된다.

**4. 안 쓰는 import**

`import java.util.Arrays;`가 남아 있는데 `Arrays`를 쓰지 않는다. 처음에 정렬로 풀려다 큐로 바꾸면서 남은 흔적으로 보인다. **정렬로 풀었어도 맞았겠지만**(`O(N log N)`), 그것도 1번과 같은 이유로 과하다.

**5. 최종본**

1~4를 합치면 이렇게 된다.

```java
import java.io.BufferedInputStream;
import java.io.IOException;
import java.io.StreamTokenizer;

public class Main {
    public static void main(String[] args) throws IOException {
        StreamTokenizer in = new StreamTokenizer(new BufferedInputStream(System.in, 1 << 16));

        in.nextToken();
        int N = (int) in.nval;

        long sum = 0, min = Long.MAX_VALUE;
        for (int i = 0; i < N; i++) {
            in.nextToken();
            long d = (long) in.nval;
            sum += d;
            if (d < min) min = d;
        }

        // 가장 짧은 트랙을 가진 친구를 허브로: 그 친구는 N-1번, 나머지는 1번씩 쓰인다
        System.out.println(sum + (long)(N - 2) * min);
    }
}
```

`N = 1`이면 `sum + (-1) * min = 0`이라 **분기가 필요 없다.** 무작위 200,000건에서 제출본과 **출력이 100% 동일**한 것을 확인했다.

| | 제출본 | 최종본 |
| --- | --- | --- |
| 계산 시간 (`N = 100,000`) | 117 ms | **21 ms** |
| 종료 시 힙 | 13.5 MB | **1.8 MB** |
| 입력이 여러 줄일 때 | 예외 | 정상 |
| 시간 복잡도 | `O(N log N)` | `O(N)` |

## 8. 배운 것

**간선 비용이 `d[a] + d[b]`처럼 두 정점 값의 합이면, MST는 최솟값 정점을 중심으로 한 별이다.** 이유는 외울 게 아니라 한 줄로 유도된다 — 트리 비용이 `Σ deg(i)·d[i]`가 되고, 차수 합은 `2(N-1)`로 고정이며 각 차수는 1 이상이니, **남는 `N-2`를 가장 싼 정점에 몰아주는 것**이 최선이다. **"간선의 집합"을 "차수 수열"로 바꿔 보는 순간 그래프 문제가 산술 문제가 된다.** 전수 조사(`n ≤ 8`)로 최적해가 항상 별이라는 것도 확인했다.

**완전그래프에서 `N`이 `10^5`면 MST 알고리즘을 쓰면 안 된다는 신호다.** 간선이 `5 × 10^9`개라 크루스칼은 정렬조차 못 한다. 서브태스크가 `N ≤ 1,000`(= `O(N^2)` 프림이 되는 크기)을 따로 40점으로 떼어놓은 것부터가 **"마지막 40점은 간선을 만들지 말고 풀어라"는 출제자의 안내**였다. 서브태스크 구성은 힌트로 읽어야 한다.

**자료구조가 만들어주는 정보를 실제로 쓰고 있는지 확인한다.** 우선순위 큐의 상품은 "순서"인데 이 문제는 그걸 다음 줄에서 버린다. 덧셈은 교환법칙이 성립하니까. 실측으로 `90ms`가 순수 낭비였다. **`log N`을 내고 산 것을 쓰지 않는다면 그 자료구조는 틀린 게 아니라 필요 없는 것이다.** 정렬해놓고 첫 원소만 쓰는 코드, `HashMap`에 넣고 `containsKey`만 하는 코드도 같은 부류다.

**`long`은 예제가 아니라 제약 조건의 곱셈으로 결정한다.** `10^5 × 10^9 = 10^14`을 미리 계산했으면 `long`은 고민거리도 아니다. 반대로 예제(`4 / 1 3 5 7 → 18`)는 `int`로도 통과하므로 **아무것도 말해주지 않는다.** 그리고 `long` 변수에 담는다고 안전한 게 아니라 **연산 하나하나가 어느 타입에서 일어나는지**를 봐야 한다 — `ans += min + next`의 덧셈은 int에서 일어났고, 여유는 7.4%뿐이었다.

**입력 형식에 대한 가정은 통과해도 검증된 게 아니다.** `readLine()` 한 번으로 `N`개를 받는 코드는 "값이 한 줄에 다 온다"는 가정에 기대고 있고, 값을 한 줄에 하나씩 주면 즉시 죽는다. **토큰 단위로 읽으면 가정 자체가 없어진다** — [나무꾼 미르코](../5170.%20나무꾼%20미르코/README.md)나 [예산](../2581.%20예산/README.md)처럼 "수열 하나를 받는" 문제 전부에 그대로 적용된다.

### 관련 문제

이 문제와 **동일한 백준 문제는 찾지 못했다.** 아래는 같은 MST 계열이지만, **전부 간선이 입력으로 주어지는 표준형**이라는 점에서 이 문제와 갈린다 — 이 문제의 핵심은 "간선을 만들지 않는 것"이다.

- [백준 1197. 최소 스패닝 트리](https://www.acmicpc.net/problem/1197) — 간선이 직접 주어지는 MST 기본형. 크루스칼/프림 연습용
- [백준 1922. 네트워크 연결](https://www.acmicpc.net/problem/1922) — 같은 기본형, 컴퓨터 연결 버전
- [백준 1647. 도시 분할 계획](https://www.acmicpc.net/problem/1647) — MST를 만든 뒤 가장 비싼 간선을 뺀다. **"MST의 성질"을 쓰는 문제**라 이 문제와 결이 가깝다
- [백준 4386. 별자리 만들기](https://www.acmicpc.net/problem/4386) — 좌표가 주어지고 거리가 간선이 되는 완전그래프. `N ≤ 100`이라 간선을 다 만들어도 되지만, **"간선이 명시되지 않는 MST"** 라는 점은 이 문제와 같다
- [백준 1774. 우주신과의 교감](https://www.acmicpc.net/problem/1774) — 완전그래프 + 이미 연결된 간선이 일부 주어지는 변형
- [백준 17472. 다리 만들기 2](https://www.acmicpc.net/problem/17472) — 격자에서 섬을 찾고(BFS) 섬 사이 간선을 만들어 MST. 간선을 **내가 만들어야 하는** 쪽
